Ти прибираєш гілки репозиторію: з'ясовуєш, що з них ще пишеться, що готове
до злиття, а що вже мертве, і доводиш дерево до стану «лишилось тільки
живе».

Аргумент команди (якщо переданий) -- поріг «покинутості» в днях, напр.
`/branches 14`. Без аргументу поріг -- **7 днів**.

## Що зібрати перед будь-якою дією

Одним заходом, не питаючи нічого в користувача:

* `git branch -vv` -- перелік, останній коміт, зв'язок з origin;
* `git branch --merged main` і `--no-merged main` -- завжди З АРГУМЕНТОМ
  `main`: без нього git рахує від поточної гілки, і список виходить про
  інше;
* `git worktree list` -- які гілки зайняті ворктрі;
* для кожної гілки: дата останнього коміта, скільки комітів попереду й
  позаду main (`git rev-list --count`);
* для гілок із ворктрі: `git status --short` у тому ворктрі.

## Як класифікувати

**Злита** -- коміти вже в main (`--merged main`). Видаляй без питань:
`git branch -d` (мала -d, щоб git сам відмовив, якщо ти помилився).

**Злита через squash або rebase** -- у `--merged` не з'явиться, бо її
комітів у main немає, є лише зліпок. Перевіряй `git cherry -v main <гілка>`:
рядки з `-` означають, що зміни в main уже є. Такі видаляй лише `-D` і лише
назвавши користувачу, що саме видаляєш.

**Жива** -- останній коміт свіжіший за поріг, АБО на ній стоїть ворктрі з
незакоміченими змінами. Не чіпай. Назви і йди далі.

**Готова до злиття** -- старша за поріг, попереду main, ворктрі чистий або
його немає. Це єдина категорія, де потрібне рішення користувача: покажи її
й спитай, перш ніж зливати.

**Сумнівна** -- усе інше (розійшлась із main сильно, має міграції, конфліктує).
Показуй, не чіпай.

## Порядок злиття, якщо користувач погодився

1. Робоче дерево мусить бути ЧИСТИМ. Незакомічені зміни -- стоп: у тому ж
   дереві може працювати паралельна сесія, і її робота не твоя. Назви файли
   й спитай, що з ними робити.
2. Зводь гілку з main У ЇЇ ВОРКТРІ (`git merge main`), а не main із гілкою:
   конфлікти тоді розв'язуються осторонь, і main весь час лишається робочим.
   Немає ворктрі -- створи тимчасовий.
3. Розв'яжи конфлікти, прожени ПОВНИЙ набір тестів там же. Червоне не
   зливається -- повертайся з тим, що зламалось.
4. Перевір `flask db heads`: якщо голів дві -- потрібна ревізія-злиток
   (id <= 32 символів), інакше `flask db upgrade` на проді відмовиться
   працювати.
5. `pybabel compile -d app/translations` -- каталоги після злиття застарівають.
6. Аж тоді `git merge <гілка>` у main і повний прогін ще раз.

## Порядок видалення

* Локально: `git branch -d <гілка>`; масово --
  `git branch --merged main | grep -vE '^\*|^\s*main$' | xargs -r git branch -d`.
* Ворктрі, що тримає гілку, прибирається ПЕРШИМ (`git worktree remove`), і
  перед тим перенеси з нього все цінне, що ігнороване git: відомості
  `.superpowers/sdd/`, локальні нотатки. Разом із текою вони зникають
  назавжди.
* Віддалені гілки -- окремо й лише за прямим дозволом:
  `git push origin --delete <гілка>`, далі `git fetch --prune`.

## Чого не робити

* Не видаляй незлиту гілку без прямої вказівки.
* Не коміть і не відкочуй чужі незакомічені зміни.
* Не пуш нічого, поки не попросять.
* Не вирішуй сам, що «тиждень без комітів = покинута», якщо на гілці лежить
  ворктрі з незбереженою роботою: це ознака живої, а не мертвої.
