Ти - експерт з веб-продуктивності: Core Web Vitals, критичний шлях рендеру, вага та пріоритизація ресурсів.

## Мета

Виміряти реальну швидкість завантаження ключових сторінок проекту IPRM, знайти вузькі місця, звести їх до конкретних файлів проекту і виправити - з обовʼязковим повторним заміром, який доводить ефект.

> **Зона відповідальності:** швидкість завантаження і відгуку сторінок - вага та порядок завантаження JS/CSS/шрифтів/зображень, критичний шлях рендеру, кешування відповідей, сторонні скрипти, LCP/TBT/CLS.
> **НЕ перевіряй:** SQL-запити та індекси (це зона `/db-optimize`), мета-теги й structured data (це зона `/seo-audit`), структуру CSS-файлів (це зона `/css-split`, `/ds-unify`).

$ARGUMENTS

Якщо аргументи не передано - повний аудит типового набору сторінок на проді (`https://plasma-regen.com`) в обох профілях.

## Інструмент

Заміри робить `tools/perf/perf_check.py` (Playwright + CDP). Повний опис метрик, бюджетів, формату JSON і обмежень - `tools/perf/README.md`. **Прочитай README перед першим запуском** і не дублюй його вміст у звіті.

Ключове, що треба памʼятати:
- профілі `desktop` (без тротлінгу) і `mobile` (CPU x4 + Slow 4G);
- у звіт іде медіана `--runs` прогонів, кеш щоразу порожній;
- вердикт сторінки `OK` / `WARN` / `FAIL` за бюджетами з `BUDGETS`;
- код повернення: `0` - все в бюджеті, `1` - є `FAIL`, `2` - нічого не виміряно, `3` - не надіслалось в адмінку;
- інструмент робить лише GET на публічні сторінки, дані не змінює;
- `--push` кладе прогін в історію адмінки (`/admin/perf`), де він автоматично порівнюється з попереднім заміром того самого сайту. Заміри на сервері НЕ виконуються: 1 ядро довелося б ділити з gunicorn.

## Контекст проекту

- Flask 3.0+ / Jinja2, базовий шаблон `app/templates/base.html` (усі CSS/JS/preload у head)
- Статика: `app/static/css/`, `app/static/js/`, шрифти `app/static/fonts/inter-*.woff2`
- Прод: nginx + gunicorn на VPS, домен `plasma-regen.com`, статика віддається з `max-age=2592000, immutable`
- GA4 ходить через first-party nginx-проксі `/ngx-i/` (див. память проекту про GA-проксі)
- reCAPTCHA підключається блоком `{% block recaptcha %}{% include 'partials/_recaptcha.html' %}{% endblock %}` у шаблонах, де є форми
- HTML віддається без кешу: обробник `no_cache_html` в `app/__init__.py`
- Зображення: WebP-варіанти через медіа-реєстр `MediaFile`

## Крок 1: Замір

```bash
python tools/perf/perf_check.py --json tools/perf/runs/before.json
```

Для точкового аудиту звузь набір: `--path`, `--profile`, більший `--runs` для стабільності.

Якщо базова лінія з попереднього аудиту вже є - додай `--baseline`, щоб одразу побачити регресії.

Збережений `before.json` знадобиться на Кроці 5 - не видаляй його.

Коли ключ приймання налаштовано (`/admin/perf`), додай `--push` і `--note` з описом стану ("до правок") - тоді історія лишиться і поза цим сеансом.

## Крок 2: Читання результатів

Розберись, ЩО саме повільно, перш ніж щось правити:

- **Високий TTFB** - проблема на сервері: повільний рендер шаблону, запити до БД, відсутність кешу. Передай у зону `/db-optimize`, якщо причина в запитах.
- **Високий LCP при нормальному TTFB** - LCP-елемент знаходиться пізно або тягнеться довго. Дивись у блоці деталізації, який ресурс має найбільший `dur`.
- **Високий TBT** - важкий JS блокує головний потік. Порівняй сумарну вагу `script` між сторінками: різниця вкаже на конкретний підключений скрипт.
- **CLS > 0** - елементи без зарезервованого місця: зображення без `width`/`height` чи `aspect-ratio`, шрифти без `size-adjust`, вміст, що зʼявляється після завантаження.
- **Велика вага при нормальних вітолах** - ризик для реальних користувачів на гіршому каналі, ніж емульований.

Обовʼязково зістав сторінки між собою: метрика погана **лише на частині сторінок** - шукай, чим їхні шаблони відрізняються; погана **скрізь** - шукай у `base.html` чи в nginx.

## Крок 3: Зведення до файлів проекту

Кожну знахідку доведи до конкретного місця в коді. Типові відповідності:

| Симптом у замірі | Де шукати |
|---|---|
| важкий сторонній скрипт на всіх сторінках | `app/templates/base.html`, `app/templates/partials/` |
| важкий скрипт лише на сторінках із формами | `{% block recaptcha %}` у відповідних шаблонах |
| шрифт довго тягнеться на mobile | `<link rel="preload">` у `base.html`, `font-display` у CSS |
| багато зображень у списках | шаблони `courses/list.html`, `trainers/list.html`, `loading="lazy"` |
| LCP-зображення пізно знайдено | preload LCP-картинки, `fetchpriority="high"`, відсутність `lazy` над згином |
| HTML не кешується / немає bfcache | `no_cache_html` в `app/__init__.py` |
| текстовий ресурс без стиснення | конфіг nginx на VPS (`/etc/nginx/conf.d/iprm.conf`) |

Не вигадуй причину - підтверджуй її читанням шаблону чи конфігу.

## Крок 4: Виправлення

Виправляй у порядку «ефект / ризик», найдешевше й найбезпечніше спершу:

1. **HIGH** - ліниве підвантаження важких сторонніх скриптів (за першою взаємодією з формою), preload/`fetchpriority` для LCP-елемента, `loading="lazy"` для зображень під згином, кешування HTML там, де воно доречне.
2. **MEDIUM** - скорочення набору шрифтових накреслень, `defer`/`async` для некритичного JS, стиснення й формати зображень, обʼєднання дрібних запитів.
3. **LOW** - мікрооптимізації, що дають одиниці мілісекунд.

Правила:
- Дотримуйся `No Inline Policy` - жодного інлайнового JS/CSS у шаблонах, тільки зовнішні файли з `app/static/`.
- Не ламай функціональність заради метрики: reCAPTCHA має спрацьовувати на реальному сабміті, аналітика - фіксувати події.
- Не додавай нових залежностей і CDN - усе self-hosted.
- Одна правка - одна причина. Не змішуй кілька оптимізацій в одну зміну, інакше повторний замір не покаже, що саме спрацювало.
- Після кожної правки вкажи файл, рядок і що саме змінено.

## Крок 5: Повторний замір

```bash
python tools/perf/perf_check.py --baseline tools/perf/runs/before.json
```

Порівняння має **довести** ефект. Якщо метрика не зрушила - визнай це прямо і не записуй правку в перемоги.

Якщо правки стосуються шаблонів, а вимірюєш прод - памʼятай, що зміни доїдуть туди лише після деплою. До деплою міряй локальний інстанс (`--base-url http://127.0.0.1:5001`) і порівнюй локальне «до» з локальним «після», не з продом.

## Крок 6: Звіт

### Загальна оцінка
2-3 речення про стан продуктивності. Окремо desktop і mobile.

### Таблиця результатів
Сторінки з колонками TTFB / FCP / LCP / TBT / CLS / load / вага / вердикт - у форматі, який друкує інструмент.

### Знахідки
Для кожної:
- симптом із конкретними числами;
- причина з посиланням на файл і рядок;
- що зроблено (або чому не зроблено);
- вимірений ефект «було -> стало».

### Що лишилось
Знахідки, які виходять за зону відповідальності або потребують рішення власника (сторонні сервіси, конфіг сервера, відмова від функціональності) - з оцінкою потенційного виграшу.

## Обмеження

- НЕ правь SQL-запити та моделі - це зона `/db-optimize`.
- НЕ правь мета-теги, sitemap, structured data - це зона `/seo-audit`.
- НЕ реорганізовуй CSS-файли - це зона `/css-split` та `/ds-unify`.
- НЕ вимикай reCAPTCHA, аналітику чи security-заголовки заради метрик - лише змінюй спосіб і момент завантаження.
- НЕ коміть і не пушай без прямого прохання.
- НЕ роби висновків без повторного заміру - цифри «до» і «після» обовʼязкові.
- Використовуй українську мову для звіту.
