# tools/ds -- інструменти зведення шару стилів

Обслуговують `/ds-consolidate` (`.claude/commands/ds-consolidate.md`).

## html_snapshot.py -- знімок вихідного HTML

Відповідає на одне питання: **чи змінилась розмітка від моєї правки**.
Потрібен там, де правка мала лишити HTML тим самим -- перехід на макрос,
винесення партіала, зведення двох написань одного компонента в одне.
Побайтовий збіг -- це доказ, що зміна не могла нічого зламати; око такого
доказу не дає.

```
python tools/ds/html_snapshot.py noise               # спершу: шум має бути 0
python tools/ds/html_snapshot.py capture --label before
...правки...
python tools/ds/html_snapshot.py capture --label after
python tools/ds/html_snapshot.py diff before after
```

Код повернення: `0` -- розбіжностей немає, `1` -- є, `2` -- знімати нема чого.

### Що заміряно на цьому проєкті

| Показник | Значення |
|---|---|
| Роутів у переборі | 128 |
| Знято сторінок (сесія адміна) | 77 |
| Знято сторінок (`--anonymous`) | 18 |
| Шум (два прогони, різні процеси) | **0** |
| Навмисна правка в один клас | рівно 1 сторінка з розбіжністю |

Різниця 77 проти 18 -- це і є причина, чому за замовчуванням інструмент
логінить адміна: без сесії 95 зі 128 роутів віддають редирект (переважно на
логін), і вся адмінка (де живе `admin.css`) у знімок не потрапляє.

### Три речі, які варто знати

**Тільки `create_app('testing')`.** Інструмент відмовляється працювати без
`TESTING`. У конфізі за замовчуванням база береться з `DATABASE_URL`
(`config.py:17`), а `create_app` наприкінці підіймає APScheduler
(`app/__init__.py:637`); єдиний запобіжник від розсилки запланованих листів
живим людям стоїть саме на `TESTING` (`app/services/scheduler_service.py:66`).
Ad-hoc скрипт із голим `create_app()` обходить обидва -- так робити не можна.

**Шум міряється у двох процесах.** В одному процесі два знімки ділять
ad-hoc TTL-кеші, що живуть у пам'яті воркера (`integration_health`,
`home_service._stats_cache`, JWKS). Перша версія цієї перевірки саме через
це показала нуль там, де його не було: `/admin/integrations` друкує час
останньої перевірки, і в межах одного процесу він брався з кешу. Виліз він
уже на справжньому `before/after`, де його не відрізнити від власної правки.

**Мови дедуплікуються.** `LocalizedBlueprint` реєструє кожне правило двічі
(`app/i18n.py:221-231`), тож голий перебір `url_map` дає ту саму сторінку
двічі, а з розкриттям префікса -- тричі. Ключ -- endpoint; `/ru`, `/en`
додаються лише явним `--langs ru,en`, бо там перевіряється переклад, а не
розмітка.

### Межі

Знімок бачить лише те, що відрендерилось:

* база порожня -- порожні стани сюди потрапляють, непорожні реєстри ні;
* сторінки з аргументом у шляху (`/courses/<slug>`) не знімаються взагалі;
* правку в тому, що не відрендерилось, знімок покаже як "змін немає".

Такі місця перевіряй окремо.

### Чому вивід не в git

`tools/ds/snapshots/` -- у `.gitignore`. У репозиторії живе інструмент, а не
його результат; те саме правило застосоване до `tools/perf/runs/`.

## ds_audit.py -- числа концепту "дизайн-система -- джерело істини"

Відповідає на чотири питання: які CSS-файли компонентні, а які
посторінкові (і скільки в кого споживачів); які класи оголошені більш
ніж в одному файлі -- саме там правка дизайн-системи до сторінки НЕ
доходить; які компонентні файли не підключені до каталогу; чиє ім'я
суперечить суті (`page-*` у компонента і навпаки).

```
python tools/ds/ds_audit.py                # повний звіт
python tools/ds/ds_audit.py --write-baseline
```

Функції `classify_css`, `duplicate_classes`, `catalog_gap`,
`naming_mismatch` імпортуються напряму іншими інструментами й тестами --
імена та сигнатури (корінь репозиторію єдиним позиційним аргументом) не
міняти.

### Що заміряно на цьому проєкті

| Показник | Значення |
|---|---|
| Компонентних файлів (2+ споживачі) | 40 |
| Посторінкових файлів | 26 |
| Дублікатів класів (клас у 2+ файлах) | 69 |
| Компонентних файлів поза каталогом | 0 |
| Розбіжностей імені й суті (`page-*`) | 0 |

### Головна пастка: споживачі рахуються транзитивно

Наївний підрахунок (хто напряму підключає файл) дає хибний результат:
`material-symbols.css` підключений з `partials/_icon_font.html` -- прямий
споживач один. Але цей партіал інклюдить `admin/base_admin.html`, який
розширюють десятки сторінок адмінки -- тобто файл насправді компонентний.
`classify_css` рахує споживачів через граф `extends`/`include`
(лише строкові літерали -- динамічний `include` потрапляє у список
`unresolved`, а не мовчки губиться). Каталог (`design_system/*.html`,
`admin/design_system*.html`) із підрахунку споживачів виключений окремо:
він ПОКАЗУЄ компоненти, а не вживає їх.

### Дублікат -- це переоголошення суб'єкта, а не будь-яка згадка класу

`duplicate_classes` рахує клас "дублікатом", лише коли він стоїть у
СУБ'ЄКТІ правила -- останній компаунд селектора, після всіх комбінаторів
і поза аргументами `:not()`/`:has()`/`:is()`/`:where()`. Причина: концепт
дизайн-системи ловить порушення "правка компонента не доходить до
сторінки", а порушує це саме ПЕРЕСТИЛІЗУВАННЯ класу, не його згадка.
`.admin-sidebar__link:has(.badge)::after {}` нічого в `.badge` не міняє --
це умова відбору, а не оголошення; такий рядок суб'єктом `.badge` не
рахує. А `.admin-instances-place .badge {}` дійсно перестилізовує
`.badge` в контексті -- і це саме той дублікат, який метрика мусить
зловити, тож він лишається. Розбір селектора винесений в окрему функцію
`_selector_subject_classes` і пришпилений тестами на літеральних рядках
CSS (`tests/test_design_system/test_ds_audit.py`), а не на живих файлах
проєкту, які з часом зміняться.

Число зі специфікації задачі (80) орієнтиром не було -- воно рахувалось
ad-hoc скриптом контролера, який до того ж пропускав чотири файли
(`fonts.css`, `material-symbols.css`, `molecular-background.css`,
`page-admin-design-system.css`). Правильне число -- те, що дає полагоджена метрика:
**69**.

### Чого тут ще немає

**Знімка обчислених стилів** (`getComputedStyle` для правок у CSS).
Він потребує браузера й піднятого сервера, тобто моделі
`tools/perf/perf_check.py` (playwright + `--base-url`), а не тестового
клієнта. Поки його немає, разовий скрипт пишеться за рецептом у Фазі 1
скіла; якщо він себе виправдав -- йому місце тут, а не в кошику.
