# perf_check - вимірювач швидкості завантаження сторінок

Лабораторний замір продуктивності публічних сторінок сайту через реальний
Chromium (Playwright + Chrome DevTools Protocol): Core Web Vitals, тайминги
навігації, вага та склад ресурсів. Метрики звіряються з бюджетами, кожна
сторінка отримує вердикт `OK` / `WARN` / `FAIL`, а код повернення робить
інструмент придатним як гейт у CI.

Інструмент робить **лише GET-запити на публічні сторінки**: даних не змінює,
форм не надсилає, у сесію не логіниться. Безпечно запускати проти продакшену.

## Встановлення

```bash
pip install playwright
playwright install chromium
```

Більше нічого не потрібно - інструмент не імпортує код застосунку і не
звертається до БД.

## Швидкий старт

```bash
# типовий набір сторінок проду, обидва профілі, 3 прогони на сторінку
python tools/perf/perf_check.py

# локальний інстанс, лише desktop
python tools/perf/perf_check.py --base-url http://127.0.0.1:5001 --profile desktop

# точковий замір конкретних сторінок з більшою кількістю прогонів
python tools/perf/perf_check.py --path / --path /courses/ --runs 5

# зберегти результат і порівняти наступний прогін із ним
python tools/perf/perf_check.py --json tools/perf/runs/before.json
python tools/perf/perf_check.py --baseline tools/perf/runs/before.json

# надіслати результат в адмінку (історія + порівняння там же)
python tools/perf/perf_check.py --push https://plasma-regen.com/api/v1/perf/runs \
    --token <ключ з /admin/perf> --note "після лінивої recaptcha"
```

Тека `tools/perf/runs/` у `.gitignore`: цифри залежать від каналу вимірювальної
машини, тож у репозиторії тримаємо інструмент, а не результати.

## Аргументи

| Аргумент | Типово | Опис |
|---|---|---|
| `--base-url` | `https://plasma-regen.com` | корінь сайту, від якого будуються шляхи |
| `--path` | типовий набір (9 сторінок) | шлях для заміру; можна вказати кілька разів |
| `--profile` | обидва | `desktop` або `mobile`; можна вказати обидва |
| `--runs` | `3` | прогонів на сторінку; у звіт іде медіана |
| `--json` | - | зберегти сирі дані прогону у файл |
| `--baseline` | - | JSON попереднього прогону для порівняння |
| `--push` | `PERF_PUSH_URL` | URL приймання в адмінці (`/api/v1/perf/runs`) |
| `--token` | `PERF_PUSH_TOKEN` | ключ приймання з `/admin/perf` |
| `--note` | - | мітка прогону в адмінці ("після лінивої recaptcha") |
| `--source` | ім'я хоста | мітка машини, з якої міряли |

## Профілі

| Профіль | Viewport | CPU | Мережа |
|---|---|---|---|
| `desktop` | 1440x900 | без тротлінгу | без тротлінгу |
| `mobile` | 390x844, DPR 2 | x4 | Slow 4G: 1.6 Мбіт/с, RTT 150 мс |

`desktop` показує верхню межу можливого - якщо повільно вже тут, проблема на
сервері або в критичному шляху рендеру. `mobile` наближений до реального
смартфона на посередньому каналі і саме він виявляє вагу JS та зображень.

Кожен прогін виконується у **свіжому контексті з порожнім кешем**, тож числа
відповідають першому візиту користувача, а не повторному.

## Метрики

| Метрика | Що означає | Звідки |
|---|---|---|
| `TTFB` | час до першого байта відповіді - робота сервера й мережі | Navigation Timing |
| `FCP` | перший контентний кадр - коли зʼявляється хоч щось | Paint Timing |
| `LCP` | найбільший контентний елемент - коли сторінка виглядає завантаженою | PerformanceObserver |
| `TBT` | сума перевищень long-task понад 50 мс - наскільки сторінка «залипає» | PerformanceObserver, lab-проксі для INP |
| `CLS` | накопичений зсув верстки | PerformanceObserver, без урахування зсувів після вводу |
| `load` | подія `load` - повне завантаження всіх підресурсів | Navigation Timing |
| `вага` | сумарний `transferSize` документа й підресурсів | Resource Timing |
| `req` | кількість запитів разом із документом | Resource Timing |

## Бюджети і вердикти

Кожна метрика має пару меж `(WARN, FAIL)`. Для `mobile` це офіційні пороги
Core Web Vitals, для `desktop` - жорсткіші, бо тротлінгу немає.

| Метрика | mobile WARN / FAIL | desktop WARN / FAIL |
|---|---|---|
| TTFB | 800 / 1800 мс | 400 / 800 мс |
| LCP | 2500 / 4000 мс | 1200 / 2500 мс |
| TBT | 200 / 600 мс | 150 / 350 мс |
| CLS | 0.1 / 0.25 | 0.1 / 0.25 |
| вага сторінки | 1200 / 2500 KB | 1200 / 2500 KB |

Вердикт сторінки - найгірший з її метрик. Після таблиці друкується блок
`ПОРУШЕННЯ БЮДЖЕТУ` з фактичним значенням і межею по кожному промаху.

Пороги задані в `BUDGETS` на початку `perf_check.py` - правити там.

### Коди повернення

| Код | Значення |
|---|---|
| `0` | усі сторінки в межах бюджету |
| `1` | є щонайменше один `FAIL` |
| `2` | жодної сторінки не виміряно (мережа, таймаут, хибний `--base-url`) |
| `3` | виміряно, але надсилання в адмінку не пройшло |

## Історія в адмінці

`--push` надсилає прогін у `/api/v1/perf/runs`, звідки він потрапляє в адмінку
на `/admin/perf`: список прогонів, розбір кожного і автоматичне порівняння з
попереднім заміром того самого сайту.

**Адмінка не вимірює сама -- і це свідоме рішення.** Прод-VPS має 1 ядро і
2 ГБ RAM без swap; headless-Chromium забирає 300-600 МБ і весь core, тож під
час заміру сайт гальмував би для відвідувачів, а метрики міряли б
перевантажений сервер замість сторінки. Рушій лишається на вашій машині,
сервер лише зберігає результат.

Налаштування:

1. `/admin/perf` -> «Згенерувати ключ». Ключ показується **один раз** -- скопіюйте одразу.
2. Запускайте інструмент із `--push` і `--token` (або задайте `PERF_PUSH_URL` /
   `PERF_PUSH_TOKEN` у змінних оточення, щоб не носити ключ у команді).
3. «Вимкнути приймання» на тій самій сторінці стирає ключ -- ендпоінт після
   цього віддає 404 будь-кому.

Що варто пам'ятати:

- Абсолютні числа з різних машин **непорівнянні**. Ставте `--source`, а
  порівнюйте прогони з однаковим джерелом -- адмінка попереджає, коли базовий
  прогін зроблено з іншої машини.
- Зберігаються останні 100 прогонів; старші видаляються автоматично при
  прийманні нового.
- Межі бюджетів їдуть разом із прогоном, тож зміна порогів у `BUDGETS` не
  переписує вердикти вже збережених замірів.

## Базова лінія і регресії

`--baseline` порівнює поточний прогін із збереженим JSON по `LCP`, `TBT` і вазі
сторінки. Регресією вважається погіршення одночасно **більш ніж на 20%** і на
абсолютний поріг (`LCP` 150 мс, `TBT` 100 мс, вага 50 KB) - інакше дрібні
коливання каналу давали б хибні тривоги. Константи: `REGRESSION_PCT` і
`REGRESSION_ABS`.

Робочий цикл при оптимізації:

```bash
python tools/perf/perf_check.py --json tools/perf/runs/before.json
# ... правки ...
python tools/perf/perf_check.py --baseline tools/perf/runs/before.json
```

## Деталізація

Для кожного профілю додатково друкується розбір **найповільнішої** сторінки:
вага документа до/після розпакування, `content-encoding` і `cache-control`,
розподіл ваги за типами ресурсів, топ-5 найважчих файлів із часом завантаження
та перелік текстових ресурсів понад 20 KB, що прийшли без стиснення.

## Формат JSON

Ключ - `"<профіль>:<шлях>"`, значення - метрики сторінки:

```json
{
  "mobile:/blog/": {
    "url": "https://plasma-regen.com/blog/",
    "status": 200,
    "ttfb": 48, "fcp": 932, "lcp": 2752, "tbt": 106, "cls": 0,
    "dcl": 1180, "load": 3414,
    "doc_transfer": 6144, "doc_decoded": 28672,
    "total_transfer": 424960, "req_count": 44,
    "by_type": {"script": {"count": 19, "transfer": 192512}},
    "heaviest": [{"name": "...", "type": "script", "transfer": 164864, "dur": 3067}],
    "uncompressed": [],
    "headers": {"content-encoding": "gzip", "cache-control": "no-cache, no-store, must-revalidate"},
    "runs_ok": 3,
    "budget": {"lcp": "WARN", "tbt": "OK"},
    "verdict": "WARN"
  }
}
```

Сторінка, яку не вдалося виміряти, має вигляд `{"url": ..., "error": "..."}`.

## Обмеження

- Це **лабораторні** дані з однієї машини, а не польові (CrUX/RUM). Вони
  показують відносні зміни й вузькі місця, але не досвід реальних користувачів.
- `TBT` - лише проксі до `INP`: він міряє блокування головного потоку під час
  завантаження, а не затримку реальних взаємодій.
- `transferSize` для cross-origin ресурсів без `Timing-Allow-Origin` дорівнює
  нулю, тож сумарна вага сторонніх скриптів може бути занижена.
- Числа залежать від каналу та завантаженості вимірювальної машини - порівнюйте
  прогони, зроблені в схожих умовах, і не змішуйте локальні заміри з проду.
- Замір іде під `load`, тому контент, що довантажується пізніше (нескінченний
  скрол, вміст під час прокрутки), у метрики не потрапляє.

## Типові сценарії

```bash
# перевірка перед деплоєм: тільки mobile, гейт по коду повернення
python tools/perf/perf_check.py --profile mobile || echo "бюджет порушено"

# сторінка, що просіла після правок
python tools/perf/perf_check.py --path /courses/ --runs 5 --profile mobile

# порівняти локальну збірку з продом (окремі файли, потім diff очима)
python tools/perf/perf_check.py --base-url http://127.0.0.1:5001 --json tools/perf/runs/local.json
python tools/perf/perf_check.py --json tools/perf/runs/prod.json
```

Автоматичний аудит із трактуванням результатів і планом виправлень -
слеш-команда [`/perf-audit`](../../.claude/commands/perf-audit.md).
