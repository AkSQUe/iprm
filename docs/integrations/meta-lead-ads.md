# Meta Lead Ads: приймання заявок з реклами

Заявки з інстант-форм Facebook та Instagram доходять до адмінки самі й
чіпляються до наявних карток людей. Ручне вивантаження таблиць із Meta
більше не потрібне.

Цей документ -- для того, хто **налаштовує** інтеграцію і хто **розбирає
її збої**. Рішення й обґрунтування -- у [плані](../plan-meta-lead-ads.md).

## Як воно працює

```
людина заповнила форму в рекламі
  -> Meta шле вебхук з ОДНИМ ідентифікатором (даних у ньому немає)
  -> POST /api/webhooks/meta/leads перевіряє підпис і кладе подію в чергу
  -> відповідає 200 і на цьому закінчує
  -> фонова джоба (щохвилини) забирає дані з Graph API
  -> нормалізує, шукає контакт, створює MetaLead
  -> заявка видно в /admin/meta-leads
```

Паралельно раз на 30 хвилин працює **звірка**: добирає з Meta заявки за
останні 48 годин і кладе в чергу ті, яких немає в базі. Вона потрібна не
«про всяк випадок» -- вебхук помирає **мовчки** (протух токен, злетіла
підписка, деплой у невдалий момент), а заявки в Meta живуть лише 90 днів.

## Налаштування з нуля

Порядок важливий: кожен крок спирається на попередній.

### 1. Meta App

Створити застосунок на developers.facebook.com. Знадобляться **App ID** і
**App Secret**.

### 2. Доступ до заявок

- роль на Сторінці Facebook з правом доступу до лідів;
- **Leads Access Manager** підтверджений для цієї Сторінки;
- розробник доданий у ролі застосунку.

### 3. App Review і Business Verification -- найдовший крок

Дозвіл `leads_retrieval` вимагає перевірки застосунку, а вона -- перевірки
бізнесу. **Доки їх немає, вебхук працює лише для людей із роллю в
застосунку** -- тобто тестова заявка дійде, а справжня від стороннього
клієнта не дійде взагалі. Це найчастіша причина «все налаштували, а заявок
немає».

Строк непередбачуваний, тож запускати цей крок треба паралельно з рештою,
а не після.

### 4. Заповнити адмінку

`/admin/meta-leads/settings`:

| Поле | Звідки |
|---|---|
| App ID, App Secret | застосунок Meta |
| Verify token | вигадати самому, знадобиться на кроці 5 |
| ID Сторінки | Сторінка Facebook |

### 5. Підписати вебхук у Meta

У налаштуваннях застосунку -> Webhooks -> Page:

- **Callback URL:** значення показане на сторінці налаштувань;
- **Verify Token:** те, що вписали на кроці 4;
- підписатись на поле **`leadgen`**.

Meta зробить `GET` на наш URL і звірить токен. Якщо не сходиться --
перевірте, що токен збережений (він шифрований, у полі показується маска).

### 6. Отримати безстроковий Page token

Кнопка **«Обміняти User token на Page token»**. У поле вставляється
короткоживучий User Access Token з Graph API Explorer; далі все
автоматично:

```
short-lived User token
  -> long-lived User token   (fb_exchange_token)
  -> Page token              (безстроковий)
```

Page token зберігається в базі **зашифрованим** і переживає перезапуск
застосунку. Ручного оновлення не потребує.

### 7. Підписати Сторінку на застосунок

Кнопка **«Підписати сторінку на leadgen»**. Це окрема дія від кроку 5:
крок 5 підписує ЗАСТОСУНОК на подію, крок 7 -- СТОРІНКУ на застосунок.
Пропущений крок 7 -- друга за частотою причина мовчання.

### 8. Перевірити

Кнопка **«Надіслати тестову подію»** будує коректно підписаний запит і
шле його на наш же публічний URL. Вона доводить одразу дві речі:
ендпоінт видно ззовні, і App Secret збігається.

Далі -- Lead Ads Testing Tool у Meta. Перед ним увімкніть **режим
тестування** (див. нижче).

## Режим тестування

Graph API не віддає надійного прапорця «це тестова заявка», тож ми
ставимо його самі: **усе, що прийшло при увімкненому режимі тестування,
позначається тестовим**. Такі заявки:

- сховані в реєстрі за замовчуванням;
- **не йдуть у MM Medic**;
- видаляються пакетно кнопкою.

Не забудьте вимкнути режим після перевірки -- інакше справжні заявки
будуть позначені тестовими й менеджер їх не побачить.

## Діагностика: заявок немає

Йти по порядку, не перестрибуючи.

**1. Токен.** `/admin/meta-leads/settings`, кнопка «Перевірити зараз».
`is_valid=false` -- див. «Ротація токена». Термін `0` означає
**безстроковий**, а не «протух».

**2. Підписка Сторінки.** Крок 7 вище. Найчастіше забувають саме його.

**3. Чи доходить вебхук.** «Надіслати тестову подію». Якщо вона не
проходить -- проблема між Meta і нашим сервером, а не в обробці.

**4. Сира черга** -- `/admin/meta-leads/events`. Якщо події там є, а
заявок немає, то ламається розбір, а не прийом. Дивіться текст помилки.

**5. App Review.** Якщо тестові заявки доходять, а справжні ні -- майже
напевно крок 3 не завершений.

**6. Просто зачекати.** Навіть при мертвому вебхуку звірка підтягне
заявки протягом 30 хвилин.

## Стани сирої події

| Стан | Що означає | Що робити |
|---|---|---|
| `pending` | ще не бралися | чекати (джоба щохвилини) |
| `retrying` | тимчасовий збій, буде повтор | чекати; backoff 1/2/4/8/16 хв |
| `done` | заявка створена | нічого |
| `skipped` | дубль -- заявка вже була | нічого, це норма |
| `failed` | спроби вичерпані | подивитись помилку, полагодити причину, «Повторити» |

Довго висить у `pending` без спроб -- майже завжди **немає токена**.
Такі події навмисно не витрачають спроби: п'ята спроба без токена не
стане валідною, а `failed` довелося б скидати руками після ротації.

## Ротація токена

`is_valid=false` означає, що токен відкликано (змінили пароль, забрали
роль, власник Сторінки відкликав доступ застосунку). Лікується повторенням
кроку 6 -- обміном нового User token. Черга при цьому нічого не втрачає:
події висять у `pending` і поїдуть, щойно з'явиться робочий токен.

Ретраїв на протухлому токені навмисно немає: повтор його не полагодить, а
спроби лише сховали б діагноз.

## Сповіщення

Менеджери зі списку в налаштуваннях сайту отримують лист, коли:

- заявок немає довше заданого періоду **при активних формах**;
- у черзі накопичились помилки;
- токен став невалідним.

Не частіше разу на добу. Листа на **кожну** заявку свідомо немає -- реєстр
із годинником очікування для цього зручніший за пошту.

Правило вмикається й вимикається окремо від решти сповіщень:
`/admin/notifications`, подія «Збій приймання лідів Meta».

## Годинник очікування

У реєстрі перша колонка -- скільки заявка чекає на першу реакцію. Три
пороги: до 15 хвилин, до години, понад. Над списком -- лічильник тих, хто
чекає понад годину.

Це не прикраса: швидкість першого дзвінка впливає на конверсію сильніше за
будь-що інше в цьому модулі. Відлік зупиняється, коли заявку переводять у
«В роботі», і **більше не запускається** -- повторне відкриття не стирає
метрику.

## Межі, які не можна порушувати

**Сира подія не видаляється ніколи.** Саме вона тримає ідемпотентність:
після видалення заявки повторна доставка того самого ідентифікатора
впізнає подію як оброблену і не воскресить видалене. Видалення заявки
лише розриває зв'язок.

**Телефон у базі НЕ унікальний.** Клініка з єдиним контактним номером --
звичайна річ, і в проді один номер справді ділять два акаунти. Тому
«точний збіг за телефоном» може дати кілька карток: заявка чіпляється до
найстарішої і позначається «потребує уваги».

**Пошта картки не перезаписується ніколи.** Це логін і унікальний ключ.
Нова адреса при збігу за телефоном лягає в поле «додаткова пошта» і
піднімає позначку для менеджера.

**Контакти не зливаються автоматично.** Якщо телефон вказує на одну
людину, а пошта -- на іншу, заявка йде до тієї, що знайдена за телефоном,
і потрапляє на ручний розбір. Телефон має пріоритет: він рідше буває
спільним і рідше вводиться з помилками.

**Нерозпізнаний номер лишається нерозпізнаним.** Канонізуються лише
українські номери. Іноземний номер зіставляється тільки за поштою --
вигадати за людину канонічну форму означало б зшити картку з ким завгодно.

## Пастки, на які вже наступили

**Вебхук мусить відповісти 200 ДО походу в Graph API.** Сам похід і був би
тим таймаутом, після якого Meta вважає доставку невдалою й починає
ретраїти. Тому ендпоінт лише кладе подію в чергу. Це закріплено тестом, що
підмінює весь HTTP-шар пасткою і перевіряє, що відповідь усе одно 200.

**Ендпоінт не гейтиться на прапорці інтеграції.** Валідно підписаний
запит приймається завжди, навіть при вимкненій інтеграції: відкинути його
означало б втратити заявку назавжди. Підпис і так відсіює чужих, а
прапорець керує обробкою, не прийомом.

**Позначка «остання заявка» рахується за часом ПРИЙОМУ, не за часом
подання.** Звірка тягне і старі заявки; від часу подання позначка їхала б
назад -- і моніторинг глушив би сам себе після кожної звірки.

**Відлік тиші для свіжої інтеграції ведеться від дати встановлення
токена.** Інакше щойно налаштована інтеграція волала б про тишу з першого
дня, ще не отримавши жодної заявки.

**Позначка «алерт надіслано» ставиться тільки після успішного
надсилання.** Інакше збій пошти вимикав би моніторинг на добу -- рівно
тоді, коли він найпотрібніший.

**Назви кампаній обрізаються під довжину колонки.** SQLite мовчки приймає
задовгий рядок, PostgreSQL падає -- тобто дефект не показався б ані в
тестах, ані локально. Назву кампанії задає рекламодавець, і 255 символів
там нічим не гарантовані.

## Передача в MM Medic

Після успішної прив'язки картки подія `lead.created` іде в партнерську
чергу -- ту саму, якою вже їдуть реєстрації та листи. Тестові заявки й
заявки без жодного контакту не йдуть.

Телефон передається **трьома ключами** (`phone`, `phone_e164`,
`phone_raw`), бо на боці партнера два різні резолвери читають його з
різних полів. Ідентифікатор нашої картки передається окремо -- на тому
боці це найсильніший ключ зіставлення.

Зворотна передача якості заявок у Meta (Conversions API) не робиться, але
структура даних для неї готова: ідентифікатор заявки, кампанії та
оголошення зберігаються.

## Маршрути

| Шлях | Призначення |
|---|---|
| `GET /api/webhooks/meta/leads` | верифікація підписки Meta |
| `POST /api/webhooks/meta/leads` | приймання подій `leadgen` |
| `/admin/meta-leads` | реєстр заявок |
| `/admin/meta-leads/<id>` | картка заявки |
| `/admin/meta-leads/events` | сира черга |
| `/admin/meta-leads/settings` | налаштування й діагностика |
| `/admin/users/<id>` | картка людини з історією заявок |
