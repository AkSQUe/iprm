# Стеля експорту міряється ДО вибірки, а не після

## Контекст

`app/admin/_listing.py` має `export_query(query, back_endpoint, **back_args)`,
написаний рівно під цю задачу: він робить `COUNT(*)`, звіряє зі стелею
`MAX_EXPORT_ROWS` і лише тоді матеріалізує зріз. Його власний докстринг
пояснює, навіщо саме такий порядок.

Ним користується **один** роут -- `meta_leads` (обидва його експорти).
Решта **дванадцять** роблять `rows = query.all()`, а стелю міряє вже
`xlsx_export` по `len(rows)` -- тобто зріз на сто тисяч рядків спершу
піднімається в пам'ять цілком, з усіма приєднаними об'єктами, і аж потім
отримує відмову. На проді це стрибок пам'яті й довгий запит, що завершується
помилкою. Найважчі кандидати -- реєстрації, сертифікати, користувачі: там і
обсяг, і найбільші join-и.

Взірець для наслідування: `app/admin/routes_meta_leads.py:366-380`.

## Spec

1. Кожен роут експорту звіряє стелю `COUNT`-ом ДО матеріалізації зрізу.
2. Поведінка при перевищенні не змінюється: те саме flash-повідомлення і той
   самий редірект на той самий зріз, що й зараз.
3. Поведінка в межах стелі не змінюється: той самий файл, ті самі рядки, той
   самий аркуш «Фільтри».
4. `xlsx_export` лишає свою перевірку `len(rows)` -- вона стає другим,
   надлишковим захистом для випадкових майбутніх викликів.

## Task 1: перевести дванадцять експортів на `export_query`

Форма правки одна, тож усі дванадцять робляться і рев'юються як одна одиниця.

Замість

```python
rows = _some_query(filters).all()
```

має бути

```python
rows, refusal = _listing.export_query(
    _some_query(filters), '<endpoint списку>', **_listing.filter_args(filters),
)
if refusal:
    return refusal
```

`endpoint` і `back_args` брати ті самі, які роут уже передає останніми
аргументами у свій `xlsx_export` -- інакше відмова поверне менеджера не на
його зріз.

### Дев'ять однакових

| Файл | Рядок | Змінна |
|---|---|---|
| `routes_b2b_requests.py` | 76 | `rows` |
| `routes_certificates.py` | 126 | `certs` |
| `routes_course_requests.py` | 96 | `rows` |
| `routes_error_logs.py` | 102 | `logs` |
| `routes_notifications.py` | 182 | `logs` |
| `routes_online_orders.py` | 378 | `orders` |
| `routes_promo_codes.py` | 132 | `promos` |
| `routes_referrals.py` | 252 | `rewards` |
| `routes_refund_requests.py` | 99 | `rows` |

### Три з особливостями -- саме тут можна тихо зламати

**`routes_registrations.py:750`** -- `regs = query.order_by(...).all()`:
сортування накладається в тому ж рядку. `export_query` усередині робить
`query.order_by(None).count()`, тож сортування для `COUNT` знімається саме
так, як треба. Передавати в `export_query` вже відсортований запит -- нормально.

**`routes_users.py:123`** -- `users_list = _users_with_counts(_users_query(filters).all())`:
результат ще й пост-обробляється. Спершу взяти рядки через `export_query`,
перевірити `refusal`, і лише потім віддати їх у `_users_with_counts`. Стеля
має спрацювати ДО пост-обробки, інакше вона рахуватиме лічильники по зрізу,
який усе одно буде відкинуто.

**`routes_instances.py:246`** -- `instances = query.limit(3).all() if next3 else query.all()`:
у гілці `next3` зріз завідомо не більший за три рядки, а `export_query` рахує
`COUNT` по ЗАПИТУ БЕЗ `limit` і відмовив би експорту, який насправді віддав би
три рядки. Стелю накладати лише на безлімітну гілку; гілку `next3` лишити як є
і пояснити це коментарем, інакше наступний «уніфікує» її назад.

## Тести

Новий файл `tests/test_routes/test_admin_export_ceiling.py`.

Головне твердження -- **порядок дій, а не лише факт відмови**. Тест, який
перевіряє тільки «прийшов редірект», проходив би і на старому коді. Довести
треба, що зріз НЕ матеріалізувався:

- підмінити `_listing.MAX_EXPORT_ROWS` на маленьке число (`monkeypatch`),
  створити більше рядків, ніж стеля;
- слухачем `before_cursor_execute` на движку зібрати всі SQL-запити;
- перевірити, що `SELECT count(` був, а повної вибірки рядків цієї таблиці
  не було;
- і що будівник xlsx не викликався взагалі (підмінити його на такий, що
  падає, -- якщо він викликаний, тест впаде сам).

Далі, по кожному з дванадцяти роутів (параметризовано одним списком, а не
дванадцятьма копіями):

- перевищення стелі дає редірект на СВІЙ список зі збереженим зрізом
  (звірити параметри в `Location`), і flash про перевищення;
- у межах стелі експорт віддає xlsx із УСІМА рядками зрізу -- не сторінкою.
  Для роутів, чиї списки пагіновані, створити більше рядків, ніж уміщує
  сторінка;
- `routes_instances.py` у гілці `next3` віддає файл навіть коли повний запит
  перевищив би стелю -- це та сама особливість, і вона мусить мати сторожа.

Кожне твердження має падати, якщо його правку відкотити. Перевірити вручну --
відкотити, побачити падіння, відновити -- і написати у звіті, що саме бачив.
На попередніх планах тричі проходили твердження, які на відкоченому коді
лишались зеленими.
