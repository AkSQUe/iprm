# Кілька тренерів на курсі та проведенні

Дата: 2026-09-10
Статус: реалізовано на гілці `sdd/course-trainers` (18 задачних комітів +
фінальні правки цілобранчевого рев'ю); у main ще не змержено, на прод не
викочено
Репозиторії: `site-iprm` (основний) + `site-mm-medic` (споживач API)

## Задача

Поле «Тренер (default)» на сторінці курсу і «Тренер» на сторінці
проведення дозволяють обрати рівно одну людину. Реальні заходи веде
двоє, троє і більше тренерів, і зараз їх нема куди записати: у картку
потрапляє один, решта не існує ні для сайту, ні для сертифікатів, ні
для розсилки.

Треба дати множинний вибір із збереженням порядку -- порядок визначає,
кого показувати першим і хто підписує сертифікат учасника.

Та сама вимога має другу половину: опис тренера не має переписуватись
до контенту заходу руками. Сьогодні редактор копіює біографію з картки
тренера в поле «Інформація про спікера», а воно не виводиться на сайті
взагалі -- робота витрачається в нікуди, і картка з полем розходяться
непомітно. Блок спікерів має збиратись із карток, а редактор -- бачити
його склад просто у формі заходу, ще до збереження.

## Погоджені рішення

1. Звʼязок -- **таблиці звʼязку з позицією**, старі колонки
   `courses.trainer_id` і `course_instances.trainer_id` прибираються.
   Денормалізованого «головного» в окремій колонці немає: два джерела
   істини розходяться, і розходження помічають не одразу.
2. **Перший у порядку = головний.** Окремої галки «головний» немає --
   позиція вже несе цю інформацію, а галка дозволила б станам
   розійтись (головний не в списку, двоє головних).
3. Сертифікат **учасника** не змінює вигляд: підпис і ПІБ лектора --
   головного тренера. Блок підпису в шаблоні один, і перелік трьох ПІБ
   у ньому ламав би верстку.
4. Сертифікат **лектора** видається кожному тренеру окремо, зі своїм
   номером і повними `bpr_lecturer_points`. Бали не діляться між
   тренерами: лекторський бал -- за проведений захід, а захід провів
   кожен із них.
5. Розсилка за правилом «Тренер заходу» йде **всім** тренерам заходу.
6. API v1: поле `trainer` **замінюється** на `trainers` (масив), без
   періоду співіснування. mm-medic мігрується в цій же роботі.
7. Онлайн-курси (`OnlineCourse.trainer_id`) **не входять** у цю
   роботу. Їхнє поле лишається одиничним -- але модель отримує
   властивість-перехідник `trainers`, бо блок тренера в них спільний
   із курсами (див. «Публічні сторінки»).
8. Поле `courses.speaker_info` **прибирається** разом із його
   перекладами, колонкою xlsx і ключем API. Воно тримало переписану
   руками біографію і не мало жодного споживача на сайті.
9. Форма заходу показує **склад блоку спікерів до збереження**:
   картку на кожного обраного тренера або адресне попередження про
   те, чого в ній бракує, з посиланням на саму картку.
10. «Картка заповнена» = є `bio`, `role` і фото. Саме ці три поля
    рендерить публічний блок; решта полів картки необовʼязкові й
    мовчки пропускаються.

## Модель даних

### Таблиці звʼязку

```
course_trainers
  course_id   BIGINT  PK, FK courses.id           ON DELETE CASCADE
  trainer_id  BIGINT  PK, FK trainers.id          ON DELETE CASCADE
  position    INT     NOT NULL

course_instance_trainers
  instance_id BIGINT  PK, FK course_instances.id  ON DELETE CASCADE
  trainer_id  BIGINT  PK, FK trainers.id          ON DELETE CASCADE
  position    INT     NOT NULL
```

Оголошення -- `db.Table`, як `role_permissions` у `app/models/rbac.py`:
власного класу-моделі тут не треба, бо крім позиції жодних атрибутів
звʼязок не має.

Складений PK замість сурогатного `id` дає унікальність пари даром:
одного тренера двічі в один курс не додати.

`ON DELETE CASCADE`, а не `SET NULL` як було в колонках. Видалення
тренера має прибирати його зі списків, а не лишати в них порожнє місце:
`SET NULL` у таблиці звʼязку означав би рядок «у курсу є тренер, і це
ніхто».

Індекс на `trainer_id` окремо -- потрібен для фільтра «показати заходи
цього тренера», який ходить у зворотному напрямку; складений PK
`(course_id, trainer_id)` для нього не годиться.

`position` без `UNIQUE(course_id, position)`: обмеження заважало б
перестановці (проміжний стан завжди має дублікат), а порядок пише одна
функція, яка нумерує з нуля без пропусків.

### Читання і запис

Читання -- звичайний `relationship`:

```python
trainers = db.relationship(
    'Trainer', secondary=course_trainers,
    order_by=course_trainers.c.position,
    viewonly=True, lazy='select',
)
```

`viewonly=True` свідомо: через `secondary` SQLAlchemy не вміє писати
додаткову колонку `position`, і мовчазна втрата порядку при
`course.trainers = [...]` була б найгіршим із можливих наслідків.
`selectinload`/`joinedload` на такому звʼязку працюють як раніше -- усі
наявні `joinedload(Course.trainer)` перетворюються на
`selectinload(Course.trainers)`.

Запис -- єдина функція в новому `app/services/trainer_links.py`:

```python
def set_trainers(entity, trainer_ids) -> None
```

DELETE усіх рядків сутності + INSERT у порядку переданого списку з
`position = enumerate`. Дублікати в переданому списку відсіюються зі
збереженням першого входження. Функція одна на обидві таблиці --
вибір таблиці за типом сутності.

### `effective_trainers`

`CourseInstance.effective_trainer` (одиничний, з fallback на курс)
замінюється на:

```python
@property
def effective_trainers(self):   # список, у порядку position
@property
def effective_trainer(self):    # перший зі списку або None
```

Семантика fallback не змінюється, лише переноситься на список:
непорожній список проведення **повністю** перекриває курсовий,
порожній -- успадковує курсовий цілком. Часткового злиття немає: якщо
проведення вказує тренерів, воно вказує їх усіх.

`effective_trainer` лишається саме тому, що місць, де потрібен рівно
один (підпис на сертифікаті, ПІБ на картці курсу), більше, ніж місць,
де потрібні всі, і кожне з них інакше писало б `[0]` з власною
перевіркою на порожнечу.

Наявний `_warn_orphan('trainer')` у `effective_trainer` (діагностика
випадку «проведення без завантаженого курсу») переїжджає в
`effective_trainers`.

### Міграція

Одна ревізія, `bpr_course_trainers_20260910`:

1. `create_table` обох таблиць звʼязку + індекси на `trainer_id`.
2. `INSERT INTO course_trainers (course_id, trainer_id, position)
   SELECT id, trainer_id, 0 FROM courses WHERE trainer_id IS NOT NULL`
   -- те саме для проведень.
3. `drop_column` `courses.trainer_id`, `course_instances.trainer_id`.
4. `lecturer_certificates`: зняти `UNIQUE(instance_id)`, поставити
   `UNIQUE(instance_id, trainer_id)`.
5. `drop_column` `courses.speaker_info` (рішення 8).

`downgrade` -- дзеркально: повернути колонки, залити в них
`trainer_id` рядка з `position = 0`, повернути `UNIQUE(instance_id)`.
Колонка `speaker_info` при відкаті повертається порожньою: її вміст --
переписані руками біографії, які вже є в картках тренерів, і
відновлювати їх нема звідки й нема навіщо.

Тренери з позицій 1+ при відкаті **втрачаються** -- це неминуче, і про
це має бути коментар у самій ревізії, а не лише тут.

Крок 4 у downgrade падає, якщо на проведення вже видано більше одного
лекторського сертифіката. Ревізія має впасти зрозуміло (перевірка
дублікатів перед створенням UNIQUE із текстом про те, які проведення
заважають), а не помилкою БД.

## Сертифікати

### Учасника

Змін у шаблоні й наборі полів немає. У `_event_snapshot`
(`app/services/certificate_service.py:196`) `instance.effective_trainer`
тепер повертає першого зі списку -- рядок коду лишається тим самим.

### Лектора

`UNIQUE(instance_id)` знімається; один запис -- це пара
«проведення + тренер».

`issue_lecturer_certificate(instance, issued_by=None)` отримує
обовʼязковий аргумент тренера:

```python
def issue_lecturer_certificate(instance, trainer, issued_by=None)
```

Ідемпотентність зберігається на новому ключі: пошук наявного йде за
`(instance_id, trainer_id)`, повторна видача повертає той самий номер.

Порядок видачі -- за `position`, щоб послідовні номери (100001, 100002,
100003) лягали за порядком тренерів, а не за порядком натискань.

`trainer_id` у `lecturer_certificates` лишається nullable з
`ON DELETE SET NULL`: сертифікат -- незмінний знімок, і видалення
тренера з довідника не має його стирати. `recipient_name` зберігає, кому
його видано. Наслідок: після видалення тренера пара стає
`(instance_id, NULL)`, і PostgreSQL вважає такі рядки різними -- тобто
UNIQUE їх не блокує. Це правильна поведінка, а не вада: два знімки на
двох різних видалених людей мусять співіснувати.

### Адмінка проведення

Маршрут `admin.instance_lecturer_certificate`
(`app/admin/routes_instances.py:369`) приймає `trainer_id` формою.
Блок у `instance_edit.html` показує рядок на кожного тренера заходу:
ПІБ, номер уже виданого сертифіката (з посиланням) або кнопку
«Видати». Кнопки «видати всім» немає -- видача кожного лишається
свідомою дією, як зараз.

Якщо тренерів у заходу немає, блок показує теперішнє повідомлення про
незаданого лектора.

## Адмінка

### Форми

`CourseForm.trainer_id` і `CourseInstanceForm.trainer_id`
(`SelectField`) стають `trainer_ids` (`SelectMultipleField`,
`coerce=int`). Хелпер `populate_trainer_choices` більше не додає
порожній пункт `(0, '– ... –')`: у мультиселекті порожнеча
виражається порожнім вибором.

Підказка під полем проведення лишається за змістом: «Залиште порожнім,
щоб узяти тренерів курсу».

`course_service.create/update` і `instance_service` замість
`entity.trainer_id = form.trainer_id.data or None` викликають
`trainer_links.set_trainers(entity, form.trainer_ids.data)`.

`course_service.duplicate` (рядок 594) копіює список тренерів разом із
порядком -- окремим викликом `set_trainers` після того, як копія
отримала `id`.

### Компонент вибору

Рендер -- наявний `data-multiselect` (`app/static/js/admin-multiselect.js`),
той самий, що на полі «Спеціальності»: чіпи з пошуком поверх нативного
`<select multiple>`.

До компонента додається впорядкування обраних: на чіпі кнопки «ліворуч»
і «праворуч». Перестановка чіпа **фізично переставляє
`<option>` у DOM прихованого `<select>`** -- браузер сабмітить обрані
значення в DOM-порядку, тож порядок доїжджає на сервер без окремого
прихованого поля з індексами.

[Реалізація] Drag НЕ побудовано -- лишились тільки кнопки ◀/▶. Перетягування
чіпів потребувало б окремої бібліотеки або custom drag-n-drop поверх
`<option>`-порядку, а кнопки вже дають той самий результат (переставляють
`<option>`) простішим кодом без миші/touch-обробки; для впорядкування
кількох тренерів у списку кнопок цілком достатньо.

Перший чіп несе позначку «головний» і пояснення в `title`, що саме його
підпис іде на сертифікат учасника.

Прогресивне покращення зберігається: без JS видно робочий нативний
мультиселект, порядок у ньому -- алфавітний (порядок `<option>`), і це
прийнятний відкат.

Правка **компонентна**: вона їде на всі сторінки з мультиселектом,
включно зі «Спеціальностями», де впорядкування доти сенсу не мало, але
й не шкодить. За правилом дизайн-системи -- показати впорядковуваний
мультиселект у `/admin/design-system`.

### Фільтр «Тренер»

Зараз фільтр реєстрацій (`app/admin/routes_registrations.py:568`)
перекладає fallback на SQL через
`func.coalesce(CourseInstance.trainer_id, Course.trainer_id)`. Зі
списками це стає:

```python
def instance_trainer_clause(trainer_id):
    """Захід веде цей тренер -- з тим самим fallback, що й у моделі."""
```

у `app/services/trainer_links.py`: `EXISTS` по
`course_instance_trainers`, АБО (за відсутності будь-якого рядка
проведення) `EXISTS` по `course_trainers` того ж курсу.

Функція одна на всіх споживачів (реєстрації, курси, звіти) -- інакше
три переклади того самого правила розійдуться, і розбіжність буде
видно лише як «у фільтрі захід є, у списку немає».

Список курсів (`routes_courses.py:61`) фільтрується простіше -- прямим
`EXISTS` по `course_trainers`, без fallback: у курсу успадковувати
нема від кого.

## Автоматичний блок спікерів

### Видалення `speaker_info`

Прибираються разом, однією роботою:

* колонка `courses.speaker_info` -- `drop_column` у тій самій ревізії;
* `CourseForm.speaker_info`, поле в `course_edit.html` разом із
  `i18n.panes`, рядки в `populate_course_from_form` і в `duplicate`;
* запис `'speaker_info': 'Про спікера'` у `translation_registry` --
  реєстр і є переліком того, що перекладається, тож окремої чистки
  таблиці перекладів не треба;
* колонка `speaker_info` в xlsx (`COURSE_COLS`, ширини, підписи).
  Файли зі старою колонкою імпортуються далі: зайві колонки імпорт
  ігнорує;
* ключ `speaker_info` у `serialize_event_detail`.

Це друга ламка контракту API поряд із `trainer` -> `trainers`. Окремого
кроку деплою вона не потребує -- їде тим самим порядком.

### Пастка: дзеркало mm-medic не самоочищається

`IprmCourse.speaker_info` заповнюється під охороною `if item.speaker_info:`
(`app/services/iprm/mirror.py:453`) -- тим самим захистом «не затирати
наявне порожнім», що й решта важкого контенту. Наслідок: коли IPRM
перестане віддавати поле, синхронізація **не прибере** старе значення,
воно лишиться в дзеркалі назавжди.

А детальна сторінка читає його першим:

```python
'speaker_info': event.speaker_info or (
    (event.trainer or {}).get('bio') if event.trainer else None
),
```

Тобто mm-medic показуватиме стару, переписану руками біографію замість
свіжої з картки -- без помилки й без ознак того, що дані застигли.

Лікування -- у міграції mm-medic (там же, де перейменування `trainer`):
`drop_column` `iprm_courses.speaker_info`, приберання поля з DTO
(`iprm/models.py:50,92,147`), з `mirror.py:453,636` і з `cache.py:257`.
Рядок вище стає просто `bio` першого тренера -- це та сама правка
`events/routes.py:393-395`, що вже описана в секції mm-medic.

Порядку деплою це не змінює: на кроці 1 mm-medic ще читає обидва
формати, на кроці 4 гілка сумісності зникає разом із колонкою.

### Прев'ю у формі заходу

Під мультиселектом тренерів -- контейнер, що показує картку на кожного
обраного: фото, ПІБ, роль, перші рядки `bio`. Перша картка несе
позначку «головний».

Джерело правди -- сам `<select>`, як у `admin-audience-preview.js`:
слухається його `change`, а не внутрішні події компонента чіпів. Це
робить прев'ю незалежним від того, чи піднявся мультиселект.

Дані -- новий `GET /admin/trainers/<id>/card.json` під тим самим
`admin_required`, що й решта `/admin/trainers`. Віддає `full_name`,
`role`, `bio`, `photo_thumb` і перелік порожніх полів. Відповіді
кешуються в памʼяті сторінки: перестановка чіпів не має ходити в мережу
за тим, що вже показано.

Чому ендпоінт, а не JSON усіх тренерів у `data`-атрибуті: тренерів
десятки, у кожного `bio` -- абзац, і вбудований масив зробив би форму
заходу помітно важчою заради даних, з яких знадобиться два-три записи.

Скрипт -- `app/static/js/admin-course-speakers.js`, зовнішній модуль,
без інлайну. Без JS прев'ю просто немає: збережений стан однаково видно
на публічній сторінці, а форма лишається робочою.

### Попередження про незаповнену картку

Замість картки прев'ю показується попередження, якщо бракує будь-чого з
трійки `bio` / `role` / фото. Формулювання адресне -- «немає біографії»,
«немає фото», а не загальне «картку не заповнено»: редактор має бачити,
що саме йти дописувати.

Поруч -- посилання «Доповнити картку» на `/admin/trainers/<id>/edit` у
новій вкладці, щоб незбережена форма заходу не втрачалась.

Попередження не блокує збереження. Захід із неповною карткою тренера --
робочий стан, а не помилка: картку часто дописують пізніше, і форма, що
відмовляється зберігатись, лише змусила б редактора прибрати тренера
зі списку.

### Дизайн-система

Картка прев'ю -- нова адмінська молекула, тож іде в компонентний
`admin.css` і **показується** в `/admin/design-system` у трьох станах:
повна картка, картка з попередженням, порожній стан «тренерів не
обрано». Компонент, якого в каталозі не видно, наступний напише
заново.

## Розсилка

`app/services/notification_recipients.py:71` замість
`instance.effective_trainer.email` збирає `email` кожного з
`effective_trainers` (поле в `Trainer` одне, окремої адреси для
сповіщень немає). `breakdown['trainer']` уже список -- структура
відповіді не змінюється, лише наповнюється циклом.

Дедуплікація за адресою -- разом з адмінами й менеджерами, як зараз:
тренер, який водночас менеджер, отримує один лист.

Правило `notify_event_trainer` і його опис в адмінці не змінюються за
змістом, лише підпис стає множинним: «Тренери заходу».

## Публічні сторінки

`partials/_course_trainer.html` -- цикл по списку. Заголовок «Ваш
тренер» / «Ваші тренери» за кількістю (обидва рядки -- через `_()`, у
трьох мовах).

Цей партіал включається **не лише** з `courses/detail.html`, а й з
`online/detail.html:235`, де `course` -- це `OnlineCourse`, який
лишається одиничним за рішенням 7. Цикл по неіснуючому атрибуту Jinja
не вважає помилкою: `{% for t in course.trainers %}` на такій моделі
рендериться порожнечею, і блок тренера мовчки зникне з усіх сторінок
онлайн-курсів -- без винятку в логах і без ознак у верстці.

Тому `OnlineCourse` отримує властивість:

```python
@property
def trainers(self):
    """Список із нуля або одного -- партіал блоку тренера спільний
    із курсами, а множинність онлайн-курсам не потрібна."""
    return [self.trainer] if self.trainer else []
```

Це шим, а не половина множинності: колонка, форма й адмінка
онлайн-курсів лишаються одиничними.

Розкладка кількох блоків -- у компонентному CSS (`iprm-trainer-block`
живе в `course-landing.css`), не в `page-*`: це поведінка компонента при
кількох екземплярах, і сторінка не має її перевизначати.

`partials/_course_card.html:91` і головна лишаються на
`effective_trainer` (одне імʼя на картці).

JSON-LD у `courses/detail.html:73` -- `instructor` стає масивом
`Person`. Один тренер віддається масивом з одного елемента:
schema.org це дозволяє, і розгалуження в шаблоні не потрібне.

## API v1

`serialize_event_card` (`app/api/v1/serializers.py:245`):

```python
'trainers': [serialize_trainer(t) for t in (
    instance.effective_trainers if instance else course.trainers
)],
```

Поле `trainer` прибирається.

[Реалізація] `serialize_trainer` таки змінюється -- отримує поле `bio`.
Партнерський блок спікера (mm-medic) переходить на нього як на єдине
джерело замість `speaker_info`, якого в API більше немає: без `bio` в
`serialize_trainer` цей блок або застигав би на старому ручному тексті,
або порожнів -- і обидва варіанти проходили б непомітно. Див. докстрінг
`serialize_trainer` (`app/api/v1/serializers.py:70-88`).

`joinedload(Course.trainer)` у `app/api/v1/events.py` (рядки 280, 281,
354, 355, 385, 386) -> `selectinload` відповідних списків. Це шість
місць, і всі шість треба перевірити на N+1 після правки: список
тренерів на списку заходів -- рівно та форма запиту, де N+1 виникає
непомітно.

## xlsx

Колонка `trainer_slug` перейменовується на `trainer_slugs`, підпис --
з «Тренер» на «Тренери».

[Реалізація] На відміну від видалення `speaker_info` (файли з тим
стовпцем і далі імпортуються -- зайву колонку `_read_sheet` просто
ігнорує), ЦЕ перейменування СТАРІ файли ламає навмисно: підпис «Тренер»
більше не збігається з обов'язковим «Тренери», і `_read_sheet` кидає
«бракує колонок» на весь sheet -- рядок не проходить частково зі
втраченими тренерами, файл не приймається взагалі. Мовчки стерти
тренерів у кожному курсі файлу було б гірше, ніж явна відмова з
зрозумілою причиною. Наслідок для експлуатації: менеджер, у якого є
вигрузка до цього деплою, мусить перевигрузити файл ПІСЛЯ нього --
старий більше не зайде.

Роздільник -- **крапка з комою**, не кома: колонка на експорті містить
ПІБ (`xlsx_io.py:772`), а ПІБ із комою («Іванов І. І., PhD») цілком
можливий. Імпорт приймає обидва роздільники -- людина, яка друкує
вручну, поставить кому.

Аркуш-довідник тренерів лишається (він потрібен людині як джерело
точних написань), але data-validation drop-down із цієї колонки
знімається: Excel не вміє валідувати клітинку з кількома значеннями, і
залишений drop-down мовчки блокував би правильне введення.

Імпорт розбиває значення, резолвить кожен елемент як slug-або-ПІБ (та
сама пара словників, що зараз) і викликає `set_trainers` у порядку
запису. Невідомі значення -- одна помилка рядка з переліком усіх
нерозпізнаних, а не падіння на першому.

## mm-medic

Автор дзеркала цю зміну передбачив: `public_trainer()`
(`app/services/iprm/mirror.py:136`) свідомо відкидає «список тренерів»
замість того, щоб зберегти невідому структуру.

### Дзеркало

* `IprmCourse.trainer` і `IprmEvent.trainer` (JSON-обʼєкт) ->
  `trainers` (JSON-масив). `public_trainer(trainer)` ->
  `public_trainers(trainers)` з тим самим білим списком полів,
  застосованим поелементно.
* `IprmEvent.trainer_id` (скалярна індексована колонка) -> таблиця
  `iprm_event_trainers(event_id, iprm_trainer_id)`, що перезаписується
  синхронізацією разом із рядком заходу.

  Не ARRAY-колонка й не JSON-вираз: причина та сама, що в коментарі до
  теперішньої колонки -- за цим полем фільтрується видимість ролі
  «Тренер», запит має бути звичайним та індексованим, і однаково
  писатись для PostgreSQL і для SQLite у тестах.
* Колонки-двійника на курсі як не було, так і немає.

### Видимість

`IprmTrainerLink` структурно не змінюється: «один акаунт -- один
тренер», обидві сторони унікальні. Змінюється лише сенс володіння --
тренер бачить захід, якщо він **серед** тренерів, а не єдиний.

`trainer_scope.owned_event_clause(trainer_id)`:
`IprmEvent.trainer_id == trainer_id` -> `EXISTS` по
`iprm_event_trainers`. `false()` при відсутньому звʼязку лишається.

### `speaker_info`

Колонка `iprm_courses.speaker_info` прибирається разом із DTO
(`iprm/models.py:50,92,147`), записом у `mirror.py:453,636` і ключем у
`cache.py:257`. Причина -- у секції «Автоматичний блок спікерів»:
залишена колонка не очищається синхронізацією і мовчки перекриває
свіжу біографію з картки.

### Решта споживачів

* `events_utils.py:118,181` і `events/routes.py:393-395` --
  `speaker` / `speaker_name` / bio беруть **перший** елемент списку.
* `cli/iprm_trainer_links.py:50` -- `flask iprm trainer-match`
  перебирає список замість одного блоку; один захід тепер може дати
  кілька пропозицій зіставлення.
* `mirror.py:633` -- payload кешу віддає `trainers=event.trainers or
  course.trainers`.

### Міграція mm-medic

Окрема ревізія: нова таблиця, перейменування JSON-колонок, перенос
наявних значень (обʼєкт -> масив з одного елемента, `trainer_id` ->
один рядок нової таблиці), видалення `trainer_id` і
`iprm_courses.speaker_info`.

Повний ресинк каталогу після деплою все одно перезапише дзеркало, але
покладатись на нього не можна: між міграцією і першим синком роль
«Тренер» не має осліпнути.

## Порядок деплою

1. **mm-medic**: міграція + код, який читає **обидва** формати --
   `trainers` (масив), а за його відсутності `trainer` (обʼєкт).
   Сумісність тимчасова, потрібна рівно на проміжок між двома
   деплоями.
2. **IPRM**: міграція + код. З цієї миті API віддає лише `trainers`.
3. Ресинк каталогу на боці mm-medic (`flask iprm sync` або чекати
   beat).
4. **mm-medic**: прибрати читання старого формату.

Пункт 4 -- не «колись потім»: залишена гілка сумісності означає, що
наступний, хто читатиме код, не знатиме, який формат актуальний.

* `OnlineCourse.trainer_id` -- одиничний. Модель отримує лише
