# Перенесення реєстрації на інший захід

Дата: 2026-08-31
Статус: затверджено до реалізації

## Мета

Дати адміністратору перенести зареєстрованого учасника з одного проведення
(`CourseInstance`) на інше -- або тихо, або «голосно»: з листом, у якому
учасник сам обирає між згодою та поверненням коштів. Разом із перенесенням
узгоджується різниця тарифів.

Сьогодні такої операції немає взагалі: єдиний спосіб перевести людину --
скасувати реєстрацію й завести нову руками, втративши історію оплати,
номер місця й зв'язок із листами.

## Рішення власника

| Питання | Рішення |
|---|---|
| Момент переїзду | **Негайно.** Згода лише підтверджує вже здійснений переїзд |
| Запобіжник «2 дні» | До **обох** заходів: і до старого, і до цільового |
| Повернення різниці тарифу | **Заявка** в чергу адміна, гроші рухає адмін |
| Учасник не доплатив різницю | Участь чинна, доплата висить як борг |
| Масове перенесення | Не в цій версії |
| Колізія з §3.2 Політики | **Два види перенесення**: з ініціативи Організатора й на прохання учасника |

## Правова рамка

Опублікована Політика (`app/templates/main/refund.html`) уже регулює
перенесення, і код мусить їй відповідати, а не сперечатись із нею:

* **§3.2** -- учасник, повідомлений про перенесення заходу, має право або
  взяти участь у нову дату **без додаткової оплати**, або отримати **повне
  повернення 100%** вартості. Не сітку 100/50/25/0 з §4.1.
* **§3.3** -- заявку на повернення через перенесення подають не пізніше ніж
  за 2 робочі дні до нової дати.
* **§4.1** -- сітка 100/50/25/0 діє, коли від участі відмовляється сам
  учасник за власною ініціативою.

Звідси головне розгалуження всієї фічі -- `initiator`:

| `initiator` | Доплата різниці | Котирування повернення |
|---|---|---|
| `organizer` | **Заборонена** (§3.2) | **100%** від сплаченого |
| `participant` | Дозволена | `refund_policy.quote_*` (§4.1) |

Заборона доплати при `initiator='organizer'` стоїть **у CHECK-обмеженні
БД**, а не лише у формі: правило родом з опублікованої оферти, і форма --
не те місце, де його можна обійти наступною правкою шаблону.

## Прийняті припущення

1. **«2 дні» -- це 48 календарних годин** від `start_date`, а не два робочі
   дні. Політика оперує робочими днями тільки в §3.3, і саме про дедлайн
   заявки на повернення, а не про перенесення. Поріг виноситься константою
   `TRANSFER_MIN_HOURS = 48` -- перехід на робочі дні лишається однією
   правкою в одному місці.
2. **Промокод при перенесенні лишається застосованим.** Перевіряти область
   дії коду заново означало б, що наше ж перенесення анулює людині вже
   надану знижку.
3. **`payment_amount` при перенесенні не змінюється.** Її рухає лише
   `payment_ops` -- при поверненні (через `refunded_amount`) або при
   зарахуванні доплати. Тариф цільового заходу фіксується знімком у
   `new_amount`, а не переписуванням суми замовлення.

## Поза межами роботи

**MM Medic не дізнається про переїзд.** `partner_events` шле
`registration.created/paid/cancelled/attended`; зміна `instance_id` не
породжує жодної події, тож у партнера лишиться старий захід. Додавати
`registration.transferred` без споживача в репозиторії mm-medic -- писати
код, який нікуди не приходить. Виноситься окремою роботою, парною до правки
в mm-medic.

## Архітектура

### 1. Модель `RegistrationTransfer` (`app/models/registration_transfer.py`)

Таблиця `registration_transfers`, один рядок на кожне перенесення.

Окрема таблиця, а не колонки на `EventRegistration`: людину можна переносити
повторно, і другий перенос не має затирати перший. `event_registrations` уже
несе понад тридцять колонок -- дописувати туди ще вісім означало б, що
кожен лістинг реєстрацій тягне поля, потрібні одному екрану.

Перевикористати `RefundRequest` теж не можна: стан згоди на перенесення --
не заявка на гроші, і партіальний унікальний індекс «одна відкрита заявка
на замовлення» зламався б від першого ж перенесення.

| Колонка | Тип | Призначення |
|---|---|---|
| `id` | `BigIntPK` | |
| `registration_id` | FK `event_registrations` CASCADE, index | чия реєстрація |
| `from_instance_id` | FK `course_instances` SET NULL | звідки |
| `to_instance_id` | FK `course_instances` SET NULL | куди |
| `initiator` | `String(20)` NOT NULL | `organizer` \| `participant` |
| `announced` | `Boolean` NOT NULL default false | голосно (лист) / тихо |
| `reason` | `String(500)` | причина переносу; NULL -> блок у листі не рендериться |
| `note` | `Text` | примітка; NULL -> блок у листі не рендериться |
| `tariff_decision` | `String(20)` NOT NULL | `keep` \| `refund_diff` \| `surcharge` |
| `to_tariff_id` | FK `instance_tariffs` SET NULL | обраний тариф цільового заходу |
| `old_amount` | `Numeric(10,2)` | знімок `payment_amount` на момент переносу |
| `new_amount` | `Numeric(10,2)` | ціна цільового тарифу на момент переносу |
| `difference` | `Numeric(10,2)` | `new_amount - old_amount` (може бути від'ємною) |
| `state` | `String(20)` NOT NULL | `applied` \| `awaiting_consent` \| `accepted` \| `refund_requested` |
| `consent_token` | `String(64)` unique, index | публічне посилання без логіну |
| `consent_token_expires_at` | `DateTime(tz)` | |
| `responded_at` | `DateTime(tz)` | коли учасник натиснув кнопку |
| `refund_request_id` | FK `refund_requests` SET NULL | породжена заявка |
| `surcharge_paid_at` | `DateTime(tz)` | коли надійшла доплата |
| `surcharge_payment_id` | `String(255)` | id платежу LiqPay |
| `created_by_id` | FK `users` SET NULL | який адмін переніс |
| `created_at`, `updated_at` | `TimestampMixin` | |

FK на заходи -- `SET NULL`, а не `CASCADE`: історія перенесення має
пережити видалення заходу, інакше зникне саме той запис, заради якого
таблиця й заводиться.

`old_amount` / `new_amount` / `difference` -- **знімки**, а не обчислення на
льоту. Той самий принцип, що вже діє в `RefundRequest.quoted_*`: тариф можна
відредагувати заднім числом, і жива формула дала б іншу відповідь, ніж та,
яку побачив учасник у листі.

**Обмеження таблиці:**

```
CHECK state IN ('applied','awaiting_consent','accepted','refund_requested')
CHECK initiator IN ('organizer','participant')
CHECK tariff_decision IN ('keep','refund_diff','surcharge')
CHECK NOT (initiator = 'organizer' AND tariff_decision = 'surcharge')   -- §3.2
UNIQUE INDEX uq_registration_transfers_open (registration_id)
      WHERE state = 'awaiting_consent'
INDEX ix_registration_transfers_registration (registration_id)
INDEX ix_registration_transfers_state (state)
```

Партіальний унікальний індекс потрібен із тієї самої причини, що й у
`refund_requests`: без нього повторний клік адміна (або двічі надісланий
лист) залишив би дві відкриті пропозиції на одну реєстрацію, і згода
учасника закривала б випадкову з них.

Властивості моделі -- за зразком інших моделей проєкту: `state_label`,
`state_badge` (модифікатор `.badge--*`), `initiator_label`,
`tariff_decision_label`, `consent_token_active`, `surcharge_due`
(`True`, коли `tariff_decision='surcharge'` і `surcharge_paid_at is None`).

### 2. Сервіс `app/services/transfer_service.py`

Уся логіка -- тут; роути лишаються тонкими. Чистий модуль поверх БД, без
знання про HTTP.

#### `check(registration, target_instance=None)` -> `list[str]`

Повертає список причин, чому перенести не можна. Порожній список -- можна.
Причини сформульовані так, щоб їх можна було показати як є (той самий
підхід, що в `refund_requests.can_request`).

Дев'ять запобіжників:

| # | Умова | Причина відмови |
|---|---|---|
| 1 | до `start_date` старого заходу < 48 год | «До поточного заходу лишилось менше 2 діб -- перенесення вже неможливе» |
| 2 | до `start_date` цільового < 48 год | «До обраного заходу лишилось менше 2 діб» |
| 3 | `target.id == reg.instance_id` | «Це той самий захід» |
| 4 | `target.status not in ('published','active')` або дата в минулому | «Захід недоступний для реєстрації» |
| 5 | у користувача вже є реєстрація на `target` | «Учасник уже зареєстрований на цей захід» |
| 6 | `reg.status == 'cancelled'` | «Реєстрацію скасовано» |
| 7 | виданий сертифікат | «За реєстрацією вже видано сертифікат» |
| 8 | `reg.quiz_passed_at` заповнено | «Учасник уже склав тест за цим заходом» |
| 9 | є відкрите перенесення (`awaiting_consent`) | «Попереднє перенесення ще очікує відповіді учасника» |

Запобіжник 5 -- не косметика: без нього перенесення падає на
`uq_user_instance_registration` рівно в момент коміту, вже після надсилання
листа.

Без `target_instance` виконуються лише перевірки, що не залежать від цілі
-- 1, 6, 7, 8, 9. Тоді сервіс відповідає на питання «чи ця реєстрація
взагалі придатна до перенесення»: якщо ні, модалка одразу показує причину й
не пропонує жодного заходу. Перевірки 2-5 -- цільові, вони й фільтрують
список у селекті.

#### `eligible_instances(registration)` -> список заходів

Проведення, що проходять запобіжники 2-5, згруповані за курсом, з тарифами
й порахованою різницею. Джерело даних для селекта в модалці.

#### `execute(registration, *, target_instance, initiator, tariff, tariff_decision, reason, note, announced, admin_user)`

Комітить. Порядок дій:

1. `check()` -- і `ValueError` зі списком причин, якщо не порожній.
   Перевірка повторюється тут, а не лише в роуті: між відкриттям модалки й
   натисканням кнопки заходи встигають змінитись.
2. Знімки: `old_amount = reg.payment_amount`, `new_amount = tariff.price`
   (або `instance.price`, якщо тарифів немає), `difference`.
3. `reg.place_number = None`, потім `reg.instance_id = target.id`.
   Знулення обов'язкове: `assign_place_number` ідемпотентний і на
   заповненому номері одразу повертає старий -- реєстрація приїхала б на
   новий захід із чужим номером місця, що ще й порушує партіальний
   унікальний індекс `uq_registrations_instance_place`.
4. `reg.tariff_id = tariff.id if tariff else None` -- інакше `tariff_id`
   лишається вказівкою на тариф чужого заходу.
5. Якщо `reg.payment_status == 'paid'` і `reg.status != 'cancelled'` --
   `registration_service.assign_place_number(reg)`.
6. Створити рядок `RegistrationTransfer`.
7. За `tariff_decision`:
   * `keep` -- нічого;
   * `refund_diff` -- `_open_refund_request(transfer, amount=abs(difference), ...)`;
   * `surcharge` -- нічого зараз; борг видно з `surcharge_due`.
8. Якщо `announced` -- видати `consent_token`, `state='awaiting_consent'`,
   надіслати лист. Інакше `state='applied'`.

`payment_amount`, `promo_code_id` і `discount_amount` не чіпаються (див.
«Прийняті припущення»).

#### `_open_refund_request(transfer, amount, reason)`

Єдина точка, що заводить заявку від імені перенесення. Обробляє колізію з
`uq_refund_requests_open_registration`: якщо на реєстрацію вже висить
відкрита заявка (типово -- на різницю тарифу), сервіс **оновлює** її суму й
причину замість створення другої. Без цього сценарій «перенесли з
поверненням різниці -> учасник передумав і попросив усе назад» падає
`IntegrityError` у момент кліку учасника.

#### `accept(transfer)` / `request_refund(transfer, reason, payout_details)`

Відповідь учасника. `accept` -> `state='accepted'`, `responded_at`,
`reg.status='confirmed'`. `request_refund` -> `state='refund_requested'` і
заявка через `_open_refund_request` із сумою:

* `initiator='organizer'` -> **100%** сплаченого (§3.2), `quoted_code='transfer_organizer'`;
* `initiator='participant'` -> `refund_policy.quote_registration(reg)` (§4.1).

Обидві -- ідемпотентні за `state`: повторний POST з тієї ж сторінки не
створює другої заявки.

### 3. Гроші

| Випадок | Сума | Механізм |
|---|---|---|
| «Поверніть кошти», `organizer` | 100% сплаченого | `RefundRequest` -> `/admin/refund-requests` |
| «Поверніть кошти», `participant` | сітка §4.1 | `refund_policy` -> та сама черга |
| `refund_diff` | \|`difference`\| | `RefundRequest` одразу при переносі |
| `surcharge` | `difference` | LiqPay, `order_id = SUR-<transfer_id>` |

Гроші не рухаються ні з модалки, ні з публічної сторінки. Це свідомо: у
проєкті вже діє правило «одне місце, де система віддає гроші» --
`payment_ops` зі сторінки повернень. Друге таке місце довелося б стерегти
окремо.

**`parse_order_id`** (`app/services/payment_ops.py`) знає лише префікси
`REG-` і `ONL-`; додається третій -- `SUR-` -> `('surcharge', <transfer_id>)`.
Обробник успішного callback заповнює `surcharge_paid_at`,
`surcharge_payment_id` і **збільшує `reg.payment_amount` на `difference`**:
саме тут сума замовлення доганяє новий тариф.

Недоплата участі не блокує (рішення власника): у реєстрі реєстрацій
з'являється плашка «доплата N грн не надійшла» і відповідний фільтр.

### 4. Лист і публічні сторінки

**`EmailService.send_transfer_offer(transfer)`** + шаблон
`app/templates/emails/transfer_offer.html`.

Це лист **учаснику**, тож `NotificationRule` не залучається. Але
`email_logs.trigger` обмежений CHECK-ом `ck_email_logs_trigger`, а
інваріант стережуть `EmailLog.TRIGGERS` і `test_trigger_coverage` -- тому
новий тригер `transfer` вимагає **міграції, що переписує CHECK**, і рядка
в `TRIGGERS`.

Зміст листа: старий захід -> новий (дата, місце) · причина *(лише якщо
заповнена)* · примітка *(лише якщо заповнена)* · тарифний блок *(лише якщо
`difference` не нульова)* · кнопки **«Погоджуюсь»** і **«Прошу повернення
коштів»** · для `surcharge` -- посилання **«Доплатити N грн»**.

Публічні роути в `app/registration/` -- дзеркало наявного токен-флоу
`/registration/complete/<token>/...`, без вимоги входу:

| Роут | Дія |
|---|---|
| `GET /registration/transfer/<token>` | сторінка з підсумком і двома кнопками |
| `POST /registration/transfer/<token>/accept` | згода |
| `POST /registration/transfer/<token>/refund` | форма причини -> заявка |
| `GET /registration/transfer/<token>/surcharge` | LiqPay на різницю |

Кнопки в листі ведуть на сторінку, а **не виконують дію GET-ом**:
пре-фетчер поштового клієнта не має вирішувати за людину. Той самий мотив,
чому `/registration/complete/<token>` -- сторінка, а не дія.

### 5. UI адмінки

**Новий компонент дизайн-системи** `modal`: `app/static/css/modal.css` +
`app/static/js/modal.js`, показаний у каталозі `/admin/design-system`.

Наявні `.iprm-confirm` (лише текст і дві кнопки) і `.media-picker`
(разовий, під бібліотеку медіа) не покривають модалку з формою. Оголосити
її всередині `page-*.css` не можна: за правилом «дизайн-система -- джерело
істини» компонент, оголошений посторінково, невидимий для наступної
сторінки, і наступний розробник напише його заново.

**Точка входу:** дія «Перенести» в меню рядка (`admin-row-menu.js`) на
`admin/instance_registrations.html` і `admin/registrations.html`.

**Поля модалки:** цільовий захід · ініціатор · тариф цільового заходу ·
рішення щодо різниці (три варіанти; «доплата» вимкнена й пояснена при
`initiator='organizer'`) · причина · примітка · галочка «сповістити
листом». Якщо `check()` повернув причини -- замість форми їх список, кнопка
неактивна.

**Роути адмінки** (`app/admin/routes_registrations.py`):

| Роут | Призначення |
|---|---|
| `GET /admin/registrations/<id>/transfer/options` | JSON: заходи, тарифи, пораховані різниці, блокери |
| `POST /admin/registrations/<id>/transfer` | виконати перенесення |

**Уся арифметика грошей -- на сервері.** JS показує те, що прийшло, і
нічого не рахує: інакше сума в модалці й сума в листі одного дня
розійдуться, і дізнаємось ми про це від учасника.
