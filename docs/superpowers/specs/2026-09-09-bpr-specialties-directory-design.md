# Довідник спеціальностей для сертифіката

Дата: 2026-09-09
Статус: реалізовано 10.09.2026 (11 комітів у main, не запушено); деплой не робився

## Задача

Поле «Спеціальності (для сертифіката)» на сторінці редагування курсу --
вільний рядок (`courses.bpr_specialties`, `String(500)`). Адміністратор
щоразу набирає назви руками, тож у сертифікат потрапляє те, що набрали:
з помилкою, у довільному відмінку, у формулюванні, якого немає в чинній
номенклатурі.

Треба зробити вибір із офіційного довідника: одна, кілька або всі
потрібні спеціальності, з пошуком і зі зняттям помилкового вибору, і
передбачити спосіб актуалізувати довідник при зміні номенклатури -- без
правки коду.

Нормативна основа: Додаток 1 до Порядку проведення атестації працівників
сфери охорони здоров'я, «Номенклатура спеціальностей / профілів роботи за
спеціальностями та відповідних їм професійних кваліфікацій / посад
працівників сфери охорони здоров'я» (`dn_650_16042025_dod_3.pdf` у корені
проєкту).

## Погоджені рішення

1. Довідник живе **таблицею в БД** зі сторінкою в адмінці, а не
   константою в коді. Актуалізація номенклатури -- робота
   адміністратора, не деплой.
2. Заводяться **розділи I-IV** Додатка 1 (лікарські, фармацевтичні,
   професіоналів, фахівців) -- приблизно 207 позицій. Блок «профілі
   роботи за спеціальностями» НЕ заводиться: це не спеціальності, і у
   виборі для сертифіката він плутав би.
3. «Усі лікарські спеціальності» -- **службове узагальнення рядком
   довідника**, а не окремий стан поля. Обирається так само, як будь-яка
   інша позиція, друкується своїм текстом.
4. Сертифікат друкує обрані назви **через кому, без ліміту кількості**.
   Довгий рядок не ламає метаблок: розмір шрифту цього рядка береться за
   довжиною, як уже зроблено для назви заходу (`event_size_class`).
5. Проведення отримує **необов'язкове перевизначення** списку. Порожньо
   -- список береться з курсу.
6. Віджет -- **прихований `<select multiple>` плюс компонент
   прогресивного покращення**. Опції рендерить сервер; чіпи, пошук і
   фільтрація -- на клієнті; без JS лишається робочий нативний
   мультиселект. Ніякого JSON-ендпойнта: 207 опцій -- це ~15 КБ у HTML
   сторінки адмінки.
7. Назви **перекладні** на ru/en через `TranslatableMixin`, як у
   довіднику локацій. Переклад належить довіднику, а не курсу.

## Номенклатура

| Розділ | `section` | Позицій |
|---|---|---|
| I. Лікарські спеціальності | `medical` | ~136 |
| II. Фармацевтичні спеціальності | `pharmacy` | 9 |
| III. Спеціальності професіоналів у сфері охорони здоров'я | `professionals` | ~29 |
| IV. Спеціальності фахівців у сфері охорони здоров'я | `specialists` | ~33 |

Числа -- оцінка за розбором PDF; точні дає парсер, і саме його вихід іде
в сид.

Плюс чотири узагальнення, по одному на розділ; у виборі стоять першими у
своєму розділі (`sort_order = 0`, тоді як позиції номенклатури нумеруються
від 1; `is_group = True`):

| code | Назва |
|---|---|
| `all-medical` | усі лікарські спеціальності |
| `all-pharmacy` | усі фармацевтичні спеціальності |
| `all-professionals` | усі спеціальності професіоналів у сфері охорони здоров'я |
| `all-specialists` | усі спеціальності фахівців у сфері охорони здоров'я |

Узагальнення пишуться з малої: у сертифікаті вони стоять після
«Спеціальності: ». Назви самих спеціальностей беруться з Додатка 1 як є.

## Модель даних

### Таблиця `specialties`

`TranslatableMixin` + `TimestampMixin` + `BigIntPK`, за взірцем
`app/models/city.py`. Файл -- `app/models/specialty.py`.

| колонка | тип | нотатки |
|---|---|---|
| `id` | BigIntPK | |
| `code` | String(60), unique, not null | латинський слаг, згенерований один раз і заморожений: `dytiacha-endokrynolohiia` |
| `name` | String(200), not null | офіційна назва з Додатка 1 |
| `section` | String(20), not null | `medical` / `pharmacy` / `professionals` / `specialists`; він же `<optgroup>` у виборі |
| `is_group` | Boolean, not null, default false | службове узагальнення |
| `sort_order` | Integer, not null, default 0 | порядок у номенклатурі |
| `is_active` | Boolean, not null, default true | знято -- зникає з вибору, але там, де вже проставлене, рендериться далі |
| `translations` | JSON | `__translatable__ = ('name',)` |

Код -- слаг, а не номер позиції: номери в номенклатурі перенумеровуються
при кожній редакції, і посилання на них розсипалось би на першій же
зміні.

### Курс і проведення

`courses.bpr_specialties` (`String(500)`, вільний текст) зникає. Замість
нього:

* `courses.bpr_specialty_codes` -- JSON, список кодів;
* `course_instances.bpr_specialty_codes` -- JSON, nullable; порожньо
  означає «як у курсу».

Поруч із `effective_cpd_points` (`app/models/course_instance.py:204`)
з'являється `effective_specialty_codes`.

`bpr_specialties` зникає з `Course.__translatable__` і з `FIELD_LABELS`
(`app/services/translation_registry.py:28`): переклад назви належить
довіднику. Це рівно та причина, що записана в шапці `app/models/city.py`
-- «Дерматовенерологія» перекладається один раз, а не в кожному курсі
заново.

### Знімок сертифіката

`certificates.specialties` і `lecturer_certificates.specialties`
лишаються РЯДКАМИ: виданий документ не має залежати від довідника, і
перейменування рядка заднім числом його не змінює. Змінюється тільки
джерело -- `', '.join` назв ефективного списку.

Обидві колонки переводяться зі `String(500)` у `Text`: ліміту на
кількість обраних позицій немає, і шість назв у 500 символів уже не
вміщаються.

## Наповнення довідника

`tools/parse_specialties.py` розбирає PDF один раз і кладе результат у
`app/data/specialties.py` -- переглянутий очима й закомічений список
кортежів `(code, name, section, sort_order)`. Міграція сіє з цього файлу.

Код будується з української назви транслітерацією (взірець --
`transliterate` у `app/services/certificate_batch.py:74`) плюс `slugify`
(`app/utils.py:180`). Той самий помічник потрібен бекфілу для незбігів,
тож він живе окремою функцією, а не всередині інструмента.

PDF у рантаймі не читається, `pypdf` у залежності проєкту не додається:
він потрібен лише тому, хто запускає інструмент.

## Міграція

Одна ревізія, щоб не плодити alembic-голів:

1. створити `specialties`;
2. засіяти позиції з `app/data/specialties.py` плюс чотири узагальнення;
3. додати `courses.bpr_specialty_codes` і
   `course_instances.bpr_specialty_codes`;
4. бекфіл: наявний текст курсу нормалізується (стиснуті пробіли, нижній
   регістр) і звіряється з назвами довідника; «усі лікарські
   спеціальності» лягає на `all-medical`;
5. будь-який незбіг заводиться рядком довідника з `is_active=False` і
   `section='medical'`, а код -- транслітерований слаг того самого тексту:
   жодне наявне значення не губиться і жоден курс не лишається з осиротілим
   кодом;
6. прибрати `courses.bpr_specialties` і ключ `bpr_specialties` з
   `courses.translations`;
7. перевести `certificates.specialties` і
   `lecturer_certificates.specialties` у `Text`.

`downgrade` повертає `String(500)`, склеївши назви через кому, і
відкидає таблицю. Рядок, довший за 500 символів, при відкаті обрізається
-- це відомий односторонній крок, пишемо про нього коментар у
`downgrade`.

## Служба `app/services/specialties.py`

Дзеркало `app/services/city_glossary.py`. Увесь довідник читається одним
запитом і кешується в `g` на час HTTP-запиту: інакше сторінка з десятком
проведень дала б десяток запитів.

Публічний інтерфейс:

* `names(codes)` -- назви активною мовою в порядку номенклатури;
* `line(codes)` -- готовий рядок для сертифіката (`', '.join`);
* `choices(current=None)` -- згруповані за розділами пари для
  `SelectMultipleField`: активні позиції плюс `current`, навіть якщо він
  деактивований;
* `effective_codes(instance)` -- список проведення або, якщо порожній,
  список його курсу;
* `usage()` -- `{code: скільки курсів і проведень}` для адмінки.

**Пастка.** У `choices` треба підмішувати вже збережені коди, навіть
деактивовані. Інакше WTForms відхилить сабміт із «Not a valid choice», і
адміністратор не збереже жодної правки старого курсу -- навіть правки
заголовка, що спеціальностей не стосується.

## Адмінка

### Сторінка `/admin/specialties`

За взірцем `app/admin/routes_cities.py`: пошук і фільтр за розділом
звужують показані рядки, збереження читає лише ті ключі форми, що
прийшли, тож збереження відфільтрованої таблиці не чіпає решту. Колонки
-- назва, розділ, ru, en, порядок, активність, лічильник використання.
Внизу -- форма додавання рядка.

Видалення дозволене лише рядку з нульовим використанням. Зайняту позицію
адміністратор натомість деактивує галкою: так актуалізація номенклатури
не лишає курси з осиротілим кодом.

### Права

Новий модуль у `app/rbac/registry.py`, поруч із `cities`:

    Module('specialties', 'Довідник спеціальностей', 'content', _VMD,
           endpoint='admin.specialties_list')

Пункт сайдбару поруч із «Довідник локацій»
(`app/templates/admin/partials/_sidebar.html`). Після деплою потрібен
`flask rbac sync`, інакше право не з'явиться в матриці; нікому, крім
`super_admin`, воно не видається автоматично.

### Форма курсу і форма проведення

`bpr_specialties` (`StringField`, `app/admin/forms.py:563`) стає
`SelectMultipleField` з `choices`, присвоєними В РОУТІ, а не на рівні
класу: довідник живе в БД, а тіло класу форми обчислюється на імпорті
модуля. Взірець -- `course_id` у `app/admin/routes_instances.py:39`.

У формі проведення поле необов'язкове; порожній вибір означає «як у
курсу», і саме так підписаний хінт.

## Компонент мультиселекта

`.admin-multiselect` оголошується в `app/static/css/admin.css` (шар
дизайн-системи, не `page-*`), поведінка -- в
`app/static/js/admin-multiselect.js`, вмикається атрибутом
`data-multiselect` на `<select multiple>`.

* обране показується чіпами з кнопкою зняття;
* поле пошуку фільтрує опції за нормалізованим підрядком;
* клавіатура: стрілки ходять списком, Enter обирає, Backspace у
  порожньому полі пошуку знімає останній чіп, Esc закриває список;
* `aria-multiselectable`, `aria-expanded`, зв'язок поля з підписом;
* без JS видно нативний `<select multiple>` -- форма лишається робочою;
* джерело правди -- сам `<select>`; компонент лише малює його стан, тож
  сабміт іде звичайним `getlist`.

Картка компонента додається у вітрину
`app/templates/design_system/_tab_*.html`. Без неї
`tests/test_design_system/test_catalog_coverage.py` червоніє -- і
правильно робить: невидимий у каталозі компонент наступний напише
заново.

## Споживачі

**Сертифікати.** `_event_snapshot`
(`app/services/certificate_service.py:196`) і лекторська гілка (`:735`)
беруть `effective_codes` проведення і `line()`. Метарядок
«Спеціальності: …» у `app/templates/certificates/certificate.html:197` і
`app/templates/certificates/certificate_compact.html:210` отримує клас
розміру за довжиною рядка -- той самий прийом, що вже вжитий для назви
заходу.

**Прев'ю сертифікатів.** Демо-дані в `app/admin/routes_tools.py:59`
переходять на коди довідника.

Більше поле ніде не читається: ні партнерське API, ні xlsx-імпорт його не
чіпають.

## Тести

* служба: порядок і локалізація назв, `effective_codes` із фолбеком на
  курс, `choices` підмішує деактивований збережений код;
* бекфіл: юніт на функцію звірки старого тексту з довідником (щоб не
  ганяти alembic у тестах) -- збіг, узагальнення, незбіг;
* форма: збереження вибору, відхилення неіснуючого коду, збереження курсу
  з деактивованою позицією;
* сертифікат: рядок для однієї, кількох і узагальненої позиції; знімок не
  змінюється після перейменування рядка довідника;
* адмінка: сторінка закрита без права `specialties.view`; видалення
  зайнятої позиції відхиляється;
* дизайн-система: наявні сторожі (`tests/test_design_system/`) мають
  лишитись зеленими -- картка компонента у вітрині і жодного дубля класу
  в `page-*`.

## Порядок деплою

Складено після фінального рев'ю 10.09.2026. Кроки 1, 2, 4 і 7 -- не
формальність: кожен з них закриває конкретний спосіб втратити дані.

1. **Зупинити воркери (Gunicorn) на час міграції.** Безпростойного шляху
   немає в жоден бік: стара кодова база читає `courses.bpr_specialties`,
   яку `upgrade()` видаляє, а нова читає `courses.bpr_specialty_codes`,
   якої до накату ще немає. Деплой коду й `flask db upgrade` мають статись
   в одне вікно простою, а не по черзі під живим трафіком.
2. **Дамп `courses(id, bpr_specialties)` ПЕРЕД накатом.** `downgrade()`
   свідомо однобічний: він склеює назви через кому й обрізає до 500
   символів, тож вихідний вільний текст після відкату не відновити нічим,
   крім цього дампу.
3. `flask db upgrade` -- ревізія `specialties_20260909`. Перед цим
   переконатись через `flask db heads`, що голова одна; якщо ланцюжок
   розгалузився, спершу `flask db merge` і застосовувати саме merge-ревізію.
4. **Звірка одразу після накату: `SELECT COUNT(*) FROM specialties`.**
   Базова лінія -- 196 (192 позиції номенклатури + 4 узагальнення).
   Більше -- частина вільного тексту не збіглася з номенклатурою і лягла
   деактивованими рядками (див. крок 7). Менше -- сидінг не відпрацював,
   зупинитись і розібратись ДО того, як на довідник почнуть посилатись.
5. `flask rbac sync` -- без цього права `specialties.*` не з'являться в
   матриці, і сторінка буде недоступна нікому, крім `super_admin`.
6. `/admin/access` -- роздати `specialties.view` / `.manage` / `.delete`
   тим ролям, кому положено.
7. `/admin/specialties`, фільтр «Деактивовані» -- **злити** кожен такий
   рядок з номенклатурною позицією, а не просто переглянути. Такий рядок
   означає вільний текст наявного курсу, що не розпізнався: курс поки
   посилається саме на нього.
8. Відкрити пару курсів у `/admin/courses` і прев'ю сертифіката: вибір
   підтягнувся, рядок «Спеціальності:» друкується так само, як до деплою.
